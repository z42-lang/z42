# 代码组织规范

## 目录 README.md

**每个功能目录必须有一个 `README.md`，描述该目录的职责、核心模块和入口点。**

适用范围：`src/` 下最多 **3 层**目录（含 `src/` 本身算第 0 层，则子目录最深到第 3 层）。

```
src/                          ← 第 1 层，不需要（已有根 CLAUDE.md）
src/compiler/                 ← 第 2 层 ✓ 需要 README
src/compiler/z42c.semantics/  ← 第 3 层 ✓ 需要 README
src/compiler/z42c.semantics/src/  ← 第 4 层 ✗ 不自动加 README
```

第 3 层的 README 应在"核心文件"或"子目录"表中覆盖其子目录的职责，不依赖子目录的 README。

### README.md 模板

**六段模板（职责 / 功能索引 / 基础用法 / 如何测试验证 / 关联文档 / 核心文件）的唯一 SoT 是
[readme-writing.md](readme-writing.md)**——本文件只管「哪一层目录需要 README」，不复制模板。

### 阅读顺序规则

**Claude 在阅读某个目录的代码前，必须先读取该目录的 `README.md`（如果存在），再决定读哪些具体文件。**

这样可以：
- 避免盲目读取无关文件浪费 token
- 快速定位关键入口，减少探索成本

### README 同步规则

何时必须同步 README，见 [doc-system.md「三问」](doc-system.md)第 3 问——**不在此另立分表**。

## 代码规模限制

### 文件行数

| 类型 | 软限制（建议拆分）| 硬限制（必须拆分）|
|------|-----------------|-----------------|
| Rust `.rs` 文件 | 500 行 | 886 行 |
| z42 `.z42` 文件 | 500 行 | 886 行 |

> **2026-09-05 调整**（软 300→500、硬 500→886）。依据：`src/` 下 1180 个非测试源文件的实际分布
> 是 中位数 122 / p90 377 / p95 467 / p99 743。旧软限 300 卡住 16.4%（194 个）却**在 lint 里
> 零实现**，是一条没人执行也没人知道失效了的死规则；旧硬限 500 虽然有门，但被咬的多是
> `YamlParser`(1692) / `BigInt`(1498) / `HttpClient`(1411) 这类**天然内聚的单一职责**，硬拆
> 反而是为拆而拆。新的 886 只留 6 个真·超大文件在棘轮里。
>
> 参照：ESLint `max-lines` 默认 300 / `max-lines-per-function` 默认 50；Checkstyle `FileLength`
> 默认 2000。业界共识是**函数长度比文件长度更承重**——本仓的函数限（40/60）目前仍是纯文档、
> 无实现，那是比放宽文件限更值得补的一环。

> 测试文件（`*_tests.rs`、`tests/<name>/` 下的 `.z42`）不计入限制，但单个测试文件超过 1000 行时也应按功能拆分。

### 函数 / 方法行数

| 限制类型 | 行数 |
|----------|------|
| 软限制（超出需要重新审视） | 40 行 |
| 硬限制（必须提取子函数） | 60 行 |

> 计算方式：函数体内的非空、非注释行数。

### 类型（struct / class / impl block）行数

| 类型 | 硬限制 |
|------|--------|
| Rust `impl` 块 | 200 行（超出拆分为多个 impl 块或子模块） |
| z42 类型（class / struct / record） | 200 行（超出提取辅助类型） |

> **类型拆多文件时累计计入**：若某语言支持把一个类型拆到多个文件（如 partial），
> 按"类型整体"判定 200 行硬限——把归属同一类型的成员体积（除模块 / 命名空间 / 类壳
> 包裹之外的部分）累加，防止"类型超 200 行"被散落到多文件来绕过。
>
> 单文件 886 行硬限仍独立适用——多文件拆分主要解决"文件超限"，**不**解决
> "类型超限"。两条限制分别约束。

### 执行方式

- **机械门禁（add-line-count-lint，2026-09-03）**：`xtask test lines` 是 GREEN gate 的一个 stage——扫 `src/` 下非测试
  `.z42` / `.rs` 文件，**新的越界文件（>886 行）或比 `scripts/test/line-limit-baseline.txt` 基线更长的已知越界文件 → 红**；软限（>500 行）只出一条 advisory 提示、不进棘轮、永不变红；
  基线内未增长的只 warn。基线是**棘轮**：拆分后降到上限以下 → `xtask test lines --update` 剔除；禁止用 `--update` 把新越界 /
  增长写进基线（那等于关掉门禁）。
- Claude 每次新增代码时，**主动检查**所在文件是否超出软限制
- 超出软限制时，**建议**拆分方案但不强制打断当前任务
- 超出硬限制时，**必须**在本次迭代内拆分，不得推迟
- 拆分是独立的 `refactor` 变更，单独 commit，不与功能变更混合
