# book 写作规范（页型 · 模板 · 图表 · 检索）

> `docs/reference/` 与 `docs/internals/` 所有页面的编写规范（`docs/learn/` 另见 learn-writing.md）。目标：**结构统一**（该图则图、该细节则细节）、
> **人和大模型都好检索**（固定骨架=稳定锚点，页头=相关性判断锚点）、
> **言简意赅**（结论句先行、只链接不复制、页长受限）。
> 文档体系定位见 [doc-system.md](doc-system.md)。

---

## 一、三种页型（每页只能是其一，写前先定）

| 页型 | 回答什么 | 落在哪本书 | 例子 |
|------|---------|-----------|------|
| **概览页** | 这部分有什么、地图在哪 | 三本书各部分的入口 | 各部分 README、全书前言 |
| **参考页** | 逐项查询（表格/条目为主，不讲故事） | **`docs/reference/`** | 语法规则、stdlib API、错误码全量表 |
| **机制页** | 为什么这样设计 + 怎么运作 + 在哪实现 | **`docs/internals/`** | GC、执行模型、自举、zbc 格式 |

**页型与书是对应的**：想清楚这页是哪一型，也就定了它属于哪本书（判据见
[doc-system.md「三本书的角色」](doc-system.md)）。`docs/learn/` 的页不在此表——它只有「章」一种形态，
写法见 [learn-writing.md](learn-writing.md)。

不允许混合体——混合体检索时不知道去哪找。内容跨页型 → 拆成两页互链，
**通常也就是拆到两本书里**（如「`where` 能写什么」进 reference、「约束检查器怎么实现」进 internals）。

## 一之二、代码块标注

- z42 源码用 ` ```z42 `；IR / 字节码 / 终端输出等非 z42 内容用裸代码块或对应语言标注。
- 语法变更时**同步更新页内的代码示例**，保持可运行 / 可解析——示例过时比没有示例更坏。
- 新增 IR 指令的参考页条目必须含：指令名、操作数类型、语义描述、伪代码示例。

## 二、统一页头（检索锚点，每页必备）

H1 下固定一个引用块。**大模型扫这两行即可判断"该不该读全页、代码去哪看"**：

```markdown
# 垃圾回收（GC）

> 对齐：2026-07-02 ｜ 代码：`src/runtime/src/gc/`
> 相关：[执行模型](execution-model.md) · [safepoint](safepoint.md)
```

- **对齐**（必备）：最后一次**与代码核对**的日期（不是修改日期）——过期检测靠它
- **代码**（必备）：权威实现的目录/文件路径
- **相关**（可选）：同书内强相关的兄弟页
- **状态**（可选，见下）

### 「状态」只记未来，不记过去

**状态字段只用来记 ToDo 与后续迭代机会**——「还差什么、下一步可以做什么」。
**已经做完的事不写状态**：页面正文描述的就是当前状态，再标一次 `✅ 已实现（0.3.x）`
是[「不写历史」](doc-system.md)禁止的过程叙述，而且必然过期。

```markdown
> 对齐：2026-09-17 ｜ 代码：`src/runtime/src/gc/`
> 待办：增量 major 的 remembered set 尚未按 card 粒度收敛；大堆 RSS 比 STW 高 30%
```

没有待办就**整个省掉这一行**。一个页头不带「状态/待办」的页，意思就是「这块目前没有已知缺口」。

> **ToDo 与历史的区别**：「**还没做 X**」是当前状态的一部分，读者需要它来判断能不能依赖这块；
> 「**2026-05-20 做了 Y**」是演进史，归 git blame 与 `docs/spec/archive/`。
> 同理，「**已知缺陷**」「**后续迭代机会**」可以写，「**曾经有过的缺陷**」不写。

## 三、机制页固定骨架（强制：H2 名称与顺序不可变）

```markdown
## 概述
[是什么、解决什么问题。1–3 句。检索摘要就靠它]

## 设计目标与约束
[要什么、不要什么]

## 方案与决策
[方案对比表 + 选型理由。重大取舍各一行"为什么不选 X"]

## 机制
[怎么运作——该图则图（见 §5）。语法特性页在此节内固定 H3：### 语法 / ### 语义 / ### 脱糖]

## 实现
[数据结构 / 算法 / 关键不变量 + 【代码地图】表：]
| 组件 | 位置 |
|------|------|
| [职责一句话] | `src/runtime/src/gc/mod.rs` |

## 边界与限制
[当前不支持什么、已知的坑]

## Deferred
[延后项，与 docs/roadmap.md Deferred Backlog Index 对接]
```

- 某节不适用可**整节省略**，但出现的节**顺序不得变、名字不得改**——锚点稳定（`gc.md#实现` 永远可链）
- 人 review 路径：看「机制」的图核对流程 → 看「实现」的代码地图抽查源码

## 四、参考页骨架

```markdown
## 概述        ← 这是什么的枚举、一句话定位
## 约定        ← 读表须知（编码、命名、单位）
## <逐项条目>   ← 每项固定：名称 / 语义 / 参数（如有）/ 示例
```

## 五、图表规则（该图则图的判定表）

| 内容形态 | 用什么 | 说明 |
|---------|--------|------|
| 流程 / 状态机 / 时序 / 分层架构 | **mermaid** | GitHub 原生渲染；Pages 站由 CI 的 mdbook-mermaid 渲染 |
| 对比 / 枚举 / 映射 | markdown 表格 | 人和模型都好读 |
| 字节格式 / 内存布局 | ASCII 定宽块 | 逐字节对齐只有等宽能表达 |
| 代码行为 | ` ```z42 ` / ` ```rust ` 代码块 | 示例保持可解析/可运行 |

**铁律：每张图必须配一段文字结论**——图渲染失败也能读懂；大模型主要读文本，图是给人的加速器。

## 六、检索与简洁规则

1. **文件名**：英文 kebab-case；**一页一主题**；H1 唯一
2. **每节首句 = 结论句**，细节在后——人扫读、模型摘要都靠首句
3. **页长软限 ~400 行**；超了拆子页挂进 SUMMARY（与代码行数限制同精神）
4. **引用代码**：`src/...` 路径 + 符号名，**不写行号**（行号必烂）
5. **跨页引用**：相对路径；**只链接、不复制**（SoT 铁律，杜绝矛盾的根）
6. **不复述代码**：代码能自明的细节不搬进文档；文档只写代码读不出的"为什么"与全局图景
7. **不重复目录 README**：基础用法/命令清单/文件职责表是 README（基础层）的地盘——book 页
   链接回对应 README，不复制（两层分工见 [doc-system.md 「三本书的角色」](doc-system.md)）

## 七、历史注记剥离（迁移与新写都适用）

**book 只描述当前状态。** `（2026-05-20 add-threading-stdlib）`这类考古注记**不进 book**——
演进史归 git blame 与 spec archive。旧 design 迁入时一律剥离；新写页面不添加。
（这是 book 与旧 design 的本质区别：design 层层追加，book 永远当前。）

同理，**对已消失事物的对照性描述也是历史**：如"C#-free / 无需 dotnet"（C# 编译器已移除，
当前状态就是纯 z42 自举，无须对照不存在的东西）。直接陈述现状，不陈述"不再是什么"。

**用语与简洁**（新写与迁移都适用）：

- **书面**：节名、术语用书面语（如「概述」而非"一句话定位"）；口语化表达（"回头调""往下走""住在"）不进正文。
- **通用**：用领域通用词，不用直译腔或生造术语——如「阶段」而非"相位"、「模块 / 包」而非"子包"、「发布产物」而非"可分发件"。拿不准某词是否通用，选更常见的那个。
- **简练**：一句能说清不写三句；概览页只给地图，细节留到对应机制页。啰嗦与越级展开都要砍（呼应 §六「每节首句 = 结论句」）。
