## 一、目标结构（end state）

重构完成后，文档收敛为**三个 docs 子目录 + 变更工作区 + 目录 README + 两个瘦入口**：

```
docs/
├── book/        【知识库·唯一SoT】mdBook（纯 markdown）——系统"是什么"：语法/机制/架构/权衡
├── workflow/    【操作手册】build / test / ci / release / debug 的具体命令
└── agent/       【面向大模型的协作材料】
    └── rules/     开发规范（流程/风格/提交…；后续可在 agent/ 下新建其它分类子目录）

docs/spec/changes/     【变更工作区】进行中 change + ACTIVE.md 账本 —— 保留
README.md              【仓库门面】首页 + 快速索引 —— 分流到 book / workflow / rules / roadmap
src/**/README.md       【目录说明】6 段制 —— 人 review 的落点
CLAUDE.md / AGENTS.md  【瘦入口】让任意大模型 import 上面的文件 —— 最后一步才配
```

> `docs/design/` **不在目标结构里**——它是待迁移的旧仓库，迁完即删（见第三节 D1/D2）。

## 二、四类文档职责（按生命周期切分）

混乱的根因是"知识 / 变更 / 规范 / 目录说明"挤在一起且互相过时。按生命周期彻底分开：

| 类别 | 是什么 | 生命周期 | 权威位置 | 受众 |
|------|--------|---------|---------|------|
| **① 知识库** | 系统当前**是什么** | 永久·永远最新 | `docs/book/` | 用户 + 维护者 + 大模型 |
| **② 变更工作区** | 一次迭代**在做什么** | 短命·做完即弃 | `docs/spec/changes/` | 大模型 + 审批的 User |
| **③ 开发规范** | 大模型/人**怎么干活** | 稳定·少变 | `docs/agent/rules/` | 大模型 + 协作者 |
| **④ 目录说明** | 某目录**有啥/怎么测/关联谁** | 随代码变 | 各 `src/**/README.md` | 人 review 入口 |

附：**操作手册**（`docs/workflow/`，怎么操作的命令）独立于以上四类。

附：**仓库门面**（根 `README.md`）——文档体系的**人的瘦入口**，与 `CLAUDE.md`/`AGENTS.md`
（大模型瘦入口）对称：只做定位 + 上手 + 快速索引，实质内容全部链接进以上四类，不承载知识。
写作规范见 [readme-writing.md](readme-writing.md)。

**SoT 铁律**：每条知识只有一个权威位置，其他地方只能链接，不得复制。发现同一事实两处各写一份
→ 按[规范冲突检测](../../../.claude/CLAUDE.md)停下，留一处、另一处改链接。

## 三、关键决策记录

| ID | 决策 | 理由 |
|----|------|------|
| **D1** | **不保留 design 作"基础层"**；"基础 vs 详细"竖切进 book（概览页=基础，深层章节=详细），不横切成两个目录 | 两份描述同一件事 → 必然漂移 = 我们要逃离的原病 |
| **D2** | `docs/design/` 定位为**待迁移旧仓库**：不再往里写新东西；新知识一律进 book；全部迁完+校对后**删除** design/ | 单一权威、消除冗余 |
| **D3** | "基础说明"= book 各部分**概览页**（`book/src/<part>/README.md`）；零散小主题 → `book/appendix/` | book 自身分层已覆盖两种深度 |
| **D4** | 正式语言规范（normative reference，Rust *Reference* 那种）**推迟到 1.0**，届时从 book 派生；现在不养两套 | pre-1.0 两三人维护，养两套必烂一套 |
| **D5** | book 用 **mdBook**（纯 markdown，`mdbook serve` 可渲染发布） | 与 Rust 技术栈一致，无额外负担 |
| **D6** | 开发规范**模型中立**，居 `docs/agent/rules/`；`CLAUDE.md`/`AGENTS.md` 仅瘦入口指进去，**最后一步**才配 | 文档为所有大模型设计，不硬绑 Claude 专属机制 |
| **D7** | `docs/spec/archive/`（590 历史目录）**暂留**，book 全面覆盖后单独清理 | 死历史 git 已留痕，不阻塞当前 |
| **D8** | 目录 README **六段制**：职责 / 功能索引 / 基础用法 / 如何测试验证 / 关联文档 / 核心文件 | 人不读源码，靠 README 快速 review（模板见 [code-organization.md](../../../.claude/rules/code-organization.md)） |
| **D9** | **README 与 book 两层分工**：README = 自足基础层（干什么/怎么用/怎么开发），book = 深入层（设计思路/实现逻辑），互链不互抄——见第四节 | 看 README 即可上手开发，查 book 才需要细节；两层各一份、不漂移 |

## 四、目录 README 与 book 的两层分工（D9 展开，2026-07-02 确立）

**核心规则：看目录 README 就能掌握"这个工具/模块是干什么的、怎么用、怎么开发"的全部
基础知识；更深的设计思路与实现逻辑细节放 book，README 链接过去。** 以 `scripts/README.md`
（xtask）为范式：项目结构、文档索引、基础用法、测试办法/流程等**面向开发的基础信息**留在
README；设计决策、编排机制、流程图进 book 工具链章节。

| 层 | 承载 | 内容 |
|----|------|------|
| **基础层** | 目录 README（六段制，D8） | 职责、项目结构、文档索引、基础用法、测试办法——自足，看完能上手 |
| **深入层** | `docs/book/` 对应章节 | 设计思路与决策、实现机制与流程图、边界与坑 |

双向纪律（防漂移）：

- README **不展开**设计原理/实现细节——需要时一句话 + 链接 book 章节
- book **不重复** README 已有的基础用法/命令清单——链接回 README
- 改代码 → README 的结构/用法段同步；改机制 → book 同步；两层各自触发

**后续所有目录文档都按此整理或修改。**

## 五、知识「上浮」规则（本体系不过时的保证）

**每个 change 归档（[workflow.md 阶段 9](../../../.claude/rules/workflow.md)）时，凡改变了语言/编译器/VM/stdlib 的对外
行为或内部机制，其知识必须上浮进 `docs/book/` 对应章节——然后变更目录随后可删（git 留痕）。**

以前 design（知识）与 spec（变更）并列，知识散落在数百个历史 change 里没人捞 → design 过时、
archive 堆到 590。用"上浮"把知识收敛到 book 单一权威，是 design 能被替换清理的前提。

## 七、行文纪律（全部文档通用，2026-07-02 确立）

适用于 book / README / workflow / 规范文档等**一切文档**：

1. **不口语化**：节名、术语、正文用书面语。反例：「一句话定位」（应为「概述」）、
   "碰巧能跑"（应为"依赖未定义顺序"）之类表达不进文档正文。
2. **不保留历史对照等过时内容**：文档只描述**当前状态**。两类都要剥离——
   - 考古注记：`（2026-05-20 add-threading-stdlib）` 这类来源日期标注，演进史归 git blame / spec archive
   - 对已消失事物的对照描述：如 "C#-free / 无需 dotnet"（C# 编译器已移除，直接陈述
     "全链 z42 自举"即可）——**说"是什么"，不说"不再是什么"**

违反即按文档过时处理：见到就改，不需要单独立项。book 专属的展开（图表配文等）见
[book-writing.md](book-writing.md) 第七节。

## 八、语种策略（沿用）

对外文档（用户/贡献者）英文；内部文档（开发流程/实现细节）中文。book 面向用户与维护者双受众，
**默认中文正文、关键术语保留英文**，成熟章节再评估是否出英文版。
