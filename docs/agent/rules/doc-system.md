# 文档体系规范

> **文档地图**（有哪些文档、三本书各给谁看、在线地址、语种）见 [docs/README.md](../../README.md)，本文件不复述。
> 本文件只管**写文档时的规则**：内容放哪、链接怎么连、改代码要补什么文档、合并前查什么。

---

## 一、内容归属

### 1.1 三层：README / 书 / agent

| 层 | 给谁 | 放什么 | 不放什么 |
|---|---|---|---|
| **README**（根 / `docs/` / 目录） | 人与 AI 的**入口** | 这里有什么、怎么用、怎么测、深入读哪页（分流导航） | 实质内容：原理、机制、完整规则 |
| **三本书** | 需要细节的人与 AI | 系统知识：语言规则（reference）、机制与决策、**操作清单与配方**（internals） | 行为约束（那是 agent 的） |
| **`docs/agent/`** | 大模型 | **规范**：流程、判据、必须 / 禁止；以及开工时去哪找 README 与书 | 系统知识；具体操作步骤；机制细节、事故案例与实测数据 |

判据一句话：**「什么情况下必须 / 禁止怎么做」是规范，归 agent；「这件事具体怎么做、为什么这样」是知识或操作，
归书；「这里有什么、去哪看」是入口，归 README。**

### 1.2 三本书之间

| | `learn` | `reference` | `internals` |
|---|---|---|---|
| **判据** | 按学习顺序读一遍就会用 | **不读实现也能用对** | **要动这块代码才需要读** |
| **组织** | 线性，后一章只依赖前面讲过的 | 按主题，可跳读，规则完整 | 按子系统，按机制 |
| **页型** | 章 | 参考页为主 + 概览页 | 机制页为主 + 概览页 + 操作页 |
| **代码** | 全部来自 `examples/`，门禁逐条重放 | 片段，说明用法 | 片段 + 伪代码 + mermaid，说明机制 |
| **明确不写** | 完整规则（链 reference）；任何实现细节 | 教学铺垫；实现机制；设计理由 | 用户用法（链 reference）；目录文件清单（链 README） |

**右边那行同样重要**——冗余都是从「顺手也写一点」开始的。页型与写法见 [book-writing.md](book-writing.md)。

### 1.3 边界裁决（容易混的，写死在这里）

| 主题 | reference 写 | internals 写 |
|---|---|---|
| 错误码 | **全量码表**（码 → 含义 → 触发示例） | 码怎么分配、如何新增一个码、诊断如何产出 |
| zbc / zpkg / IR | **不写**（用户不需要知道产物格式） | 完整格式规格（`internals/formats/`） |
| 运行时设置 | 旋钮**清单**与取值语义 | 五层优先级如何归并、旋钮登记表机制 |
| `z42.toml` | 字段全表（契约） | `BuildLayout` 级联默认的实现 |
| 泛型 | `where` 能写什么、报什么错 | 约束检查器、TSIG、单态化策略 |
| GC | **不写**（除非有用户可感知的旋钮 → 归运行时设置） | 全部 |
| 测试 | `[Test]` 怎么写、`z42 test` 怎么用 | 反射发现、runner 协议、GREEN gate 组成 |
| CLI | `z42`（面向用户的命令面） | `z42c --dump-*`（编译器调试）、`xtask *`（仓库开发） |
| 嵌入 | C ABI **契约**（宿主开发者也在「用 z42」） | VM 内部如何实现这套 ABI |
| stdlib | 公开 API、语法覆盖、不支持项 | Tier 归属、extern 预算、怎么加一个包 |

### 1.4 不是书的位置

- **PR 描述**：只记这一次迭代（方案 / 进度 / 验证），长期知识合并前上浮进书（见 §三）。
- **`docs/roadmap.md`**：计划与 Deferred 索引，不放知识。
- **`docs/` 根目录的临时迭代底稿**：迭代完成即删除；届时未完成的项转入 internals 对应页的 `## Deferred`。

## 二、链接方向（硬规则）

### 2.1 层与层之间

```
docs/agent/  ──链──▶  README、三本书     ✅ 允许，且是首选
README       ──链──▶  三本书             ✅ 允许
三本书 / README ─链─▶  docs/agent/        ❌ 不允许（链接即引用）
```

- **稳定性**：agent 改动最频繁（一次整合就可能删并若干文件），书与 README 链过去就会静默断链——跨书引用多是
  绝对 URL，死链检查**查不到**。
- **受众**：书的读者不该被带进「AI 怎么干活」的流程层。
- **唯一例外**：根 `README.md` 与 `docs/README.md` 的分流导航——它们是总入口，不指路会让贡献者找不到规范。
- **代码注释、脚本、CI 配置同理**：不写 `docs/agent/` 路径；要交代事实或做法，指向书里讲这件事的页。
- 书 / README 需要引用某条规范时，用**不带链接的散文**陈述事实（写「pre-1.0 不留兼容」，而不是链到规则标题）。
- 由 `xtask test docs` 的 ③ 机械校验（豁免自动生效）。

### 2.2 三本书之间

```
learn  ──链──▶  reference          internals  ──链──▶  learn / reference
                    │                   ▲
                    └──── 正文不得链 ────┘
```

**面向用户的两本书（learn / reference）的正文里，不出现任何指向 `internals/` 的链接**（绝对 URL 也算）。
需要交代「实现细节在别处」时，用不带链接的散文（「具体降解过程属实现细节，本手册不展开」）。

**唯一例外**：每本书首页（`src/README.md`）的「去哪」导航表可以列出另外两本书，一行链接、不复述内容。

## 三、改代码要补什么文档：三问

**每个 PR 合并前，凡改变了对外行为或内部机制的，知识必须在同一个 PR 内上浮进书**；目的地由三问决定，不由作者偏好决定：

1. **用户能看见吗？**（语法 / stdlib API / CLI / 清单字段 / 诊断文本 / 产物格式）
   → `reference` 对应页必改；该特性若已被 learn 覆盖 → `examples/<章节>/` + learn 章一并改。
   stdlib API 的 reference 页是生成物（不入库，发布时由 `xtask doc gen` 从源码生成）：**改源码的 `///` / `//!`**，
   不手改页面；要看效果就本地 `xtask doc gen`
2. **下一个接手的人不读文档能看懂吗？**（多阶段编排 / 有状态或累积的循环 / 反直觉决策与踩过的坑 /
   跨组件或跨进程协议）
   → `internals` 对应机制页必改
3. **目录的结构、对外入口或依赖变了吗？**
   → 该目录 `README.md` 必改（改哪段见 [readme-writing.md](readme-writing.md)）

**三问全否 = 纯内部重构，不补文档**——也不许顺手改文档制造漂移。
拿不准第 2 问算不算「复杂」→ **停下问 User**，别默默略过。

## 四、三道门

| 门 | 内容 |
|---|---|
| **① 同一个 PR** | 文档与代码同分支同 PR。禁止「代码先合、文档后补」 |
| **② `xtask test docs`** | 机械检查：① 相对链接可解析；② gate stage 清单与 test-gate 文档一致；③ 书 / README / 代码不引用 agent；④ `src/` 第 2、3 层的目录 README 有「关联文档」段。`xtask test docs examples` 另查 learn ↔ examples（B1–B10，含 learn 的 SUMMARY 对账）并重放会话脚本 |
| **③ 合并前 doc-check** | 人工兜底，清单如下 |

**合并前 doc-check 清单**（全部勾上才能合并）：

- [ ] 三问逐条过一遍，命中的文档均已更新
- [ ] 所改目录的 README 必备段齐全（模板见 [readme-writing.md](readme-writing.md)）
- [ ] 所改 / 新写的书页：描述的是当前状态、代码路径可解析、已挂入所属书的 `SUMMARY.md`
- [ ] `xtask test docs` 绿
- [ ] **删 / 改 / 重命名任何命令面**（xtask 子命令、CLI verb、工程文件字段、脚本入口）时，
      `grep -rn "<旧名>" docs/ scripts/ AGENTS.md` 清零——命令面重构的文档半径系统性被低估，门禁不查这一项

## 五、防漂移

1. **SoT 铁律**：一条事实只有一个权威位置，其余只能链接。发现同一事实两处各写一份 →
   按[规范冲突检测](philosophy.md#规范冲突检测必须遵守)停下，留一处、另一处改链接。
2. **不写历史**：文档只描述**当前状态**——不写来源 / 日期标注，不写迁移与演进过程，不拿已消失的东西作对照，
   不写版本号这类会随迭代变化的值。演进史归 git 历史与 PR 描述。
3. **但「还没做什么」要写**——它是当前状态的一部分，读者靠它判断能不能依赖。禁的是回头看，不是向前看。
   **写在哪（唯一口径）：**

   | 位置 | 写什么 |
   |---|---|
   | 页头「待办」行（可选） | 本页已知缺口的一行摘要，没有就整行省掉 |
   | internals 机制页 `## 边界与限制` / reference 参考页 `## 不支持` | 当前不支持什么、已知的坑（不打算排期的也写） |
   | internals 机制页 `## Deferred` | 登记过的延后项（格式见 [philosophy.md 延后特性管理](philosophy.md#延后特性管理必须遵守)），每条在 `docs/roadmap.md` 的 Deferred Backlog Index 有索引行 |
   | 目录 README `## 待办` | 只与本目录绑定的那几条 |

违反即按文档过时处理：见到就改，不需要单独立项。
