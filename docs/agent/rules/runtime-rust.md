# Rust VM 开发规范

> 写 `src/runtime` 及 native 扩展时的约定。VM 的机制在书里，入口见[开工导航](../README.md#开工先找-readme-和书)的「虚拟机」行。

## 跑 cargo

- **cargo 只经 xtask 跑，或在 `src/runtime/` 目录里跑，或显式带 `--config src/runtime/.cargo/config.toml`**：仓库根下
  `cargo … --manifest-path src/runtime/Cargo.toml` 读不到这份配置，产物会落进 `src/runtime/target/` 而不是
  `artifacts/build/runtime/`。

## 模块边界与公开面（必须遵守）

新增模块、跨模块引用、公开类型或组件能力时，先列出状态所有者、消费者和接口类别，再选文件位置与可见性。
当前实现与目标边界见[运行时模块边界](../../internals/src/runtime/module-boundaries.md)，实施顺序只在
[roadmap](../../roadmap.md#runtime-module-boundaries运行时模块边界收口)维护。

1. **区分宿主接口、VM 内部接口、同构建跨库协议。** 默认使用私有、`pub(super)` 或 `pub(crate)`；
   `host` 只提供宿主确实需要的加载、调用、配置及功能级诊断请求，不因为内部模块已有 `pub` 就转出。
   禁止从 `host` 具名或通配再导出组件管理/协议 API；公开签名也不得传递组件 ID、工厂、描述符、注册表、
   管理选项或接口租约。执行模式等宿主意图与组件装配结构分别定义。
2. **VM 消费者经 `components::api` 访问组件能力。** 此处指 crate 内部访问门面，不是面向普通嵌入端的 SDK API。
   消费者不得引用组件实现 crate、具体实现类型，或穿透 `catalog`、`instance`、`backends`、`profiling` 等管理子模块。
   消费者按稳定的能力/接口版本及语义角色请求服务，不传具体实现的 ComponentId、库名或入口符号。
   具体实现的路径、命名、发现与装配差异由组件层及其适配器吸收；能力接口不暴露这些差异。
   多实现的选择在装配时明确绑定，缺失或歧义显式报错，不按注册先后猜测提供方。
3. **跨 crate 必需的协议不经 host 绕行。** 独立后端共享的描述符、C 布局表和最小同构建 Rust 桥另列契约边界，
   记录真实消费者与寿命/身份约束。Rust 跨 crate 所需的 `pub` 不等于对普通宿主公开；禁止借此批量再导出 VM 子系统，
   或将整个组件管理实现纳入协议。组件入口、静态链接胶水与普通宿主调用分开验证。
4. **策略在装配入口解析，机制消费显式输入。** 组件管理、执行、诊断、加载等机制不反向读取进程配置来决定策略，
   不依赖 host 实现。状态由一个所有者保存，其他模块使用最小只读视图、能力接口或注入回调，不能为了方便传整个 VmContext。
   低层契约不引用高层具体实现；对象表示、GC、线程等必要协作须声明数据/屏障/暂停契约，不能把所有双向引用一概视作错误。
5. **查询、准备与执行分开。** 能力/接口查询只读已知状态，不隐式装库、创建实例或执行托管代码；显式准备操作才触发依赖加载、
   校验及事务发布。初始化失败逆序回滚，worker 共享所属 VM 的组件状态，接口调用保留正确代码寿命。
   执行热路径使用装配时绑定的能力，不为统一入口逐指令查组件表。
6. **三种使用形态分别建模和验证。** 静态链接、作为共享库依赖的动态链接、运行时 dlopen/LoadLibrary 装入分别记录来源；
   不能以一个 Dynamic 或 Linked 名称混同后两者/前两者。消费者的能力接口保持相同，装配层按构建能力、实际来源、平台支持和
   运行时允许策略检查，再验证 ABI/核心身份、依赖与寿命；不回落到被禁止的形态。静态/链接动态实现可能已由系统装入，
   运行时禁用控制启用/实例化，不代替构建裁剪。协议及验证矩阵见[组件化运行时](../../internals/src/runtime/componentized-runtime.md#组件三种使用形态目标契约)。
7. **审查与验证覆盖边界本身。** PR 列出变更前后的所有者、公开面与新增依赖边；收口实现须包含普通宿主可用的正向消费者、
   内部 API 不可达的编译失败用例，以及真实组件/静态链接胶水的正向构建。依赖检查区分生产、测试、宏/生成代码和平台实现，
   不用宽泛豁免或仅改 import 拼写隐藏依赖。历史缺口如实记录，新代码不得扩展它们。

## 文件命名与职责（必须遵守）

- Rust 文件采用 `snake_case`，用「领域 + 职责」表达内容。`*_config` 表示解析后的配置值，`*_policy` 表示策略，
  `*_registry` 表示注册/查询事实，`*_loader` 表示装入机制，`*_dispatch` 表示调用派发，`*_abi` 表示二进制协议；
  `api` 只表示明确消费者的访问门面，不能同时代指组件协议和管理实现。
- 跨子系统容易混淆的 `state.rs`、`config.rs`、`native.rs`、`types.rs`、`utils.rs` 等应按实际职责细化。
  不给每个文件机械加前缀；`mod.rs`/`lib.rs`/`main.rs`、同一 PAL 契约的平台镜像和明确的私有领域子模块允许同名。
- 一个文件承担策略、发现、装载、注册或调用等多个独立职责时，先调整抽象/所有者，再拆分与命名；不能用重命名代替依赖收口。
  搬动实现不应迫使能力消费者修改具体组件路径。
- 重命名同步模块声明、调用点、测试、README 与书页，不保留旧名转发或兼容别名；测试与实现保持同名 `*_tests.rs`。

## 错误处理

- 可能失败的函数返回 `anyhow::Result<T>`；内部 VM 错误（非用户错误）用 `bail!` / `anyhow!`。
- **非测试代码禁止 `unwrap()` / `expect()`**；测试代码可以用。
- 运行时值类型不匹配时报错，**不做静默转换**。

## 测试文件组织

单元测试放独立文件，不内联在实现文件末尾：`foo.rs` 的测试放同级 `foo_tests.rs`，`foo.rs` 末尾只留
`#[cfg(test)] mod foo_tests;`；集成测试放 crate 级 `tests/`。目的：读实现时不被测试占掉上下文。

## 原生代码与 GC（必须遵守）

触发条件：写 builtin / corelib / native 扩展，或任何让 Rust 代码持有、写入 z42 堆值的地方。四条规则，具体做法、
参照实现与测试形状见[原生代码与 GC 的协作约定](../../internals/src/runtime/native-gc-contract.md)：

1. **根集之外不持有 z42 值**：值优先做成 z42 对象的字段；只能暂存时必须钉住（pin）并由守卫负责释放。
2. **可能长时间不返回的 native 调用必须 park**：park 区间内不分配、不跑 z42 代码、不攥着共享锁。新增会阻塞的
   builtin 要带 park 计数的单测和一次阴性对照。
3. **写堆引用只走带写屏障的原语**，批量写也一样；新增在堆里存引用的布局时，屏障与「开屏障存活 / 关屏障被扫」
   测试随写入原语一起加。
4. **wasm 上不取时钟**：关着的探针不取时钟，始终要跑的计时给 wasm 替代实现。

## 执行模式

- 尚未覆盖的后端 / 路径必须明确报错，不返回伪结果或静默降级；按 PR 声明的能力与场景验收。
- 新能力按 interp → JIT → AOT 推进，先验证 interp 契约，再扩展其他后端；已有后端的修复按受影响模式验证。

## 引入依赖

**触发条件**：要给 Rust VM / native 层加新依赖，或动手实现一个有成熟先例的子系统。

- 优先用成熟开源库，只在无合适库或需要深度定制时自行实现；引入前按 [philosophy.md](philosophy.md) 评估，
  并在 `Cargo.toml` 注明用途。
- 动手前先查已调研的候选库与参考项目：[运行时 · 依赖与参考实现](../../internals/src/runtime/README.md#依赖与参考实现)。
