# z42 人机协作工作流（以 Pull Request 为单位）

## 核心模型

**一个 PR 交付一个逻辑单元。** User 定目标与裁决分歧；AI 在授权内完成探索、实施、验证、合并与清理。
PR 描述记录本轮目标、方案、进度、决策与验证；长期知识按 [doc-system 三问](doc-system.md)同步到所属文档。
已有明确授权写回描述即可，不重复确认；需要询问的情况统一见[越界防护](#越界防护)。

**源码注释只写持久约束。** 不变量、等价性前提、并发边界和维护陷阱留在源码；测量数据、日期戳、
事故回放与迁移过程写进 PR。保留仍有效的结论，删去过程叙事；归档路径与生成器文件头中的日期不受此限。

## 持续迭代与持续发起 PR

User 要求持续迭代或自动推进时，记录目标、范围与完成条件，在该范围内循环：

1. 检查实现、测试与已有 PR，选择有证据、可验证的缺口；开放式目标不要求预先列尽 PR。
2. 每轮独立 worktree、分支与 PR；同一项的修正更新原 PR，不重复开 PR，也不为凑数量制造改动。
3. 持续跟进自己的审查反馈、CI 与冲突，按阶段 5–6 验证和合并；等 CI 时可推进不依赖它的下一项。
4. 合并后完成清理，再基于最新 main 进入下一轮，汇报结果与下一步，不等待 User 再说「继续」。
5. 目标完成、范围内已无有价值的可执行项、User 要求暂停，或存在无法排除的外部阻塞时，报告状态；
   未授权取舍按越界防护处理，需中断的未完成工作按阶段 6 交接。

持续迭代不降低 Spec-First、测试、文档同步与合并门禁。

## PR 即在制品账本

- `gh pr list`（含 draft）查看在制品；只修改当前任务拥有的 PR / 分支，不接管其他会话的工作。
- 当前进度、方案与授权依据看 PR 描述；历史决策用 `git log -S<符号>` → 提交标题 `(#N)` → `gh pr view N` 追溯。
- 分支名用动词开头的 kebab-case，≤ 5 词；PR 标题与提交格式见 [commit-log.md](commit-log.md)。

## 变更分类

**按实际行为变化分类，不能靠提示词或文件数判断。**

| 类型 | 触发条件 | 描述要求 |
|---|---|---|
| `lang` / `ir` / `vm` | 新增或改变语言、IR / 格式、VM 或公开接口契约 | 完整模式，实施前完成 Spec-First |
| `fix` / `refactor` | 恢复既有契约或不改行为的内部调整 | 最小模式；多步骤时列任务清单 |
| `test` / `docs` | 只改测试或文档 | 最小模式，直接实施 |

拿不准是否改变契约时先核对 reference / internals；存在实质歧义才询问。
「直接做」不免除实际语义变更的完整模式；讨论或整理新语法的文档也不自动等于实施新语法。

## 🔴 Spec-First Self-Check（lang / ir / vm 强制）

第一行实现前，draft PR 必须已有阶段 2 的完整方案，并按阶段 3 记录授权依据。
长期文档或聊天记录不能代替 PR 中的本轮方案；已有明确授权无须再次审批。

## 阶段 0：意图识别

**分析仓库前必须先同步最新版本，纯分析、审查和目录 / 命名建议同样适用。**

1. 先检查工作区、分支与 worktree 状态，再执行 `git fetch origin`，以最新 `origin/main` 为分析基线。
2. 干净且可快进的主树切到 `main` 后执行 `git merge --ff-only origin/main`；有未提交改动、分叉或其他会话正在使用时，
   不覆盖、不重置，另建基于最新 `origin/main` 的隔离 worktree 阅读。
3. 记录分析基线 SHA，再读该版本的规范、README 与源码；继续旧任务时先核对最新 main 的相关变化，修正过时结论。
4. 无法 fetch 时明确报告更新失败与本地版本，不能将旧快照称为最新版本。User 明确指定历史版本或 PR 时按指定版本分析，
   并标明目标版本及其与最新 main 的关系。

先理解当前指令；恢复任务时读取相关 memory（不入库）、roadmap 与当前 PR，简报状态和下一步。
只要求分析时保持只读；要求实施或持续整理时按授权推进。「继续」按[会话恢复协议](#会话恢复协议)执行，
「暂停」立即停止自动推进并保存状态。

## 阶段 1：探索（Explore）

1. 按[开工导航](../README.md#开工先找-readme-和书)读相关 README、书页与源码，确定问题、风险和验收条件。
2. 对照 roadmap 的当前阶段与既有决策，识别受影响组件、前置依赖及同范围在制 PR。
3. 有实质取舍时提出选项与推荐；目标和方案已明确时自主选定并进入阶段 2。
   探索本身不要求创建 PR、分支或方案文件。

## 阶段 2：开工——分支、worktree、PR 描述

**每次改动使用专属 worktree 与分支，禁止在共享主树直接修改。**
先 fetch，基于最新 `origin/main` 建树；供种后按本树源码重建 xtask，做法见
[开发环境](../../internals/src/devinfra/dev-setup.md)。

- **完整模式**：先开 draft PR，再实施；可用空提交承载方案，squash 后主线只留最终逻辑单元。
- **最小模式**：直接实施，GREEN 后开 PR；需要 CI 定位时可提前开 draft，完成条件见阶段 5。

**完整模式描述：**

```markdown
## Why / What
[问题、目标与变化；修改既有行为时给 Before / After]

## Spec
- WHEN <正常条件> THEN <结果>
- WHEN <边界 / 异常条件> THEN <结果>
[lang / ir：IR Mapping 与受影响的 Pipeline Steps]

## Design
[架构、关键决策与理由、测试策略；图仅在有助说明时使用]

## Scope
[目标、完成条件；具体文件路径与 NEW / MODIFY / DELETE / RENAME 类型]
[排除项、Deferred 与待裁决问题；没有时省略]

## 任务
- [ ] <可验证结果及涉及文件>

## 验证
base: <main sha>
head: <最终验证提交 sha；尚未提交时待补>
[阶段 5 的验证结论]
```

最小模式只需 **What / Why、文档影响、验证**；多步骤补任务清单。
Scope 文件清单不得使用通配符或「相关文件」等模糊描述，每条变更关联任务；实施中按实际需要更新，
是否扩展授权按越界防护判断。Spec 场景与任务清单在实施前写明，不能事后补成实施依据。

## 阶段 3：实施前确认（Gate）

### 单 PR 模式（默认）

- 最小模式：User 已要求完成该变更即可实施，不额外等待「开始」。
- 完整模式：已有明确授权覆盖 PR 方案时，记录依据后继续；尚未授权的行为或架构取舍展示摘要并请 User 裁决。
- User 调整方案后先更新描述；只对新引入的未授权取舍重新确认。

### 批量授权模式（Batch Approval）

User 授权一组 PR / 计划时，记录目标、清单、依赖与授权依据，按依赖自动实施、验证、合并和接续。
固定清单只授权该组；开放式持续迭代按已授权目标选题。每个 PR 仍须独立通过门禁并同步文档。
授权覆盖范围内的实施、commit、push、开 PR、合并与本轮清理；权限边界统一见越界防护，
不因 CI 配置等文件类型额外索要确认。

## 阶段 4：实施（Apply）

按任务实施并更新 PR 进度；按有意义的结果汇报，不逐个代码操作报幕。
编译器变更按依赖推进：Lexer → Parser / AST → TypeChecker → Codegen → VM → 测试与文档；无关阶段不凑步骤。

实施中运行相关编译与测试，失败按阶段 5 处理；范围内的调整写回 PR，未授权取舍按越界防护处理。
可继续不受失败影响的工作，但不得带着相关失败把本 PR 标为完成。

## 阶段 5：验证（Verify）

**最终 GREEN 只认完整 `xtask test`，任一必跑阶段失败都不得标 ready 或合并。**
在仓库根执行：

```bash
./xtask test
```

- 开发时可用 `test changed`、单 stage 或 `--no-build` 缩窄验证，但不能代替最终 GREEN。
- stage 组成与执行机制见 [GREEN gate](../../internals/src/devinfra/test-gate.md)；按改动选择附加验证见
  [怎么跑测试](../../internals/src/devinfra/testing.md)。发行版 / 跨平台 / 嵌入接口变更追加 `xtask package sdk --verify`。
- **最终提交前通过 GREEN**；草稿 PR 可推送明确标为未完成的过程提交，用于 CI 定位和协作。

| 失败类型 | 处置 |
|---|---|
| 本次引入或暴露的相关缺陷 | 本轮修复；无法修复时报告证据，不把失败当成通过 |
| 变更前已存在或与本轮目标无关 | 记录复现与范围，按授权另开 PR / issue，不混入当前逻辑单元 |
| 环境、权限或外部服务导致 | 排除环境问题后重跑受影响检查；不能验证时如实报告阻塞 |

另开跟踪项不等于豁免门禁；最终 GREEN 未通过仍不得合并。
PR 的验证段写 **base sha、验证 head、命令与结果**；完整模式另列 Spec 覆盖与任务完成情况。

## 阶段 6：合并（Merge）

1. **同步文档**：按 [doc-system 三问与 doc-check](doc-system.md)检查；根 README 的维护触发见
   [readme-writing.md](readme-writing.md)，协作流程变化更新 agent，计划与 Deferred 变化更新 roadmap。
   文档与代码同 PR 落地，不在合并后补推 main。
2. **定稿描述**：记录最终目标、实际 Scope、关键决策、Deferred 与验证结果，合并后作为档案。
3. **提交**：只暂存本变更路径，按 [commit-log.md](commit-log.md)提交，不用 `git add -A` 混入其他文件。
4. **同步并合并**：先 fetch 并入最新 main；未发布分支可 rebase，已发布分支默认 merge 后普通 push，避免改写远程历史。
   ```bash
   git fetch origin
   git merge --no-edit origin/main
   ./xtask test
   git push origin <branch>
   gh pr ready                             # 仅 draft 需要
   gh pr merge --squash --delete-branch --match-head-commit <验证head>
   ```
   有冲突时保留双方有效意图，处理文件移动、编号碰撞与可由现有规范确定的语义适配，更新调用点与测试；
   不整片选 ours / theirs 丢弃另一方改动。解决后提交冲突修复、重跑 GREEN、推送并跟进 CI。
   远端 head 必须与验证提交一致，所需 CI / 审查已通过；**base、代码或产物前提变化使验证失效时重跑**，
   最新 main 未变化且同一最终内容已通过完整 GREEN 时无需重复执行。合并前确认 main 未前进，不绕过分支保护。
   squash 后 main 一个 PR 一个提交，正文写 ≤ 10 行 Why / What 与关键决策，完整记录留 PR。
5. **合并后清理（必做，默认授权）**：确认 PR 已合并、应交付的内容已落地后，清理本轮本地工作文件、
   远程 / 本地分支与专用 worktree；清理完成才算本轮收尾。
   - **清理范围**：本轮创建且不再需要的临时脚本、补丁、PR 描述草稿、日志、测试输出、性能原始数据、
     下载归档、临时副本与构建产物；worktree 外的本轮临时目录和文件也要清理，不能只删分支。
   - **先保存再删除**：必要的决策、验证结论与性能证据在合并前写入 PR 或所属长期文档；未完成任务的交接信息
     按第 6 步保存。交付文件、未提交改动、其他会话的文件，以及仍被后续任务使用的种子 / 共享缓存不得误删。
   - **按归属清理**：只删除能确认属于本轮且已无使用者的文件；检查 worktree 的未提交与未跟踪文件，
     不用强制删除或全目录清空掩盖遗漏。确需保留的文件说明路径、用途与后续清理时机。
   ```bash
   git worktree remove <worktree-path>      # 有未提交改动时会拒绝——先确认没漏东西
   git branch -d <branch>                   # 本地分支
   git push origin --delete <branch>        # 远程分支（用 --delete-branch 合并时已删）
   ```
   清理自己这条已合并 PR 的临时工作文件、分支与 worktree 属**默认授权**，无需逐项询问；完成后简报清理结果与保留项。
   force-push / 删他人分支仍需单独确认（阶段 3 边界）。
6. **继续或交接**：有已授权后续项就进入下一轮；需中断时才保存 memory 与简短续推口令。
   memory 写目标与授权、已合并 PR / 决策、未完成项 / 阻塞、工作区与种子位置、验证配方和下一步。

### 并行与合并顺序（多 PR in-flight）

- **先就绪先合，不预先排队。** 文本冲突在同步 main 时解决，语义耦合靠同步后的完整 GREEN 验证；
  深度耦合的 PR 在描述中标明依赖，不能靠文件不重叠判断互不影响。
- 改动影响编译产物时，合并前至少一轮冷验证，避免热缓存掩盖错误；做法见[怎么跑测试](../../internals/src/devinfra/testing.md)。
- 测试工具若要拿新 runner 检查旧 base，所需源码修复须独立先合，避免本地新树全绿而旧 base 无法执行。
- 全局唯一编号按合并顺序让号：先入 main 者保留，后者更新登记与引用。诊断码见
  [错误码全表](../../reference/src/appendix/error-codes.md)；diagcodes 检查不替代同步 main 与完整 GREEN。

## 会话恢复协议

User 说「继续」时，读取当前 PR 的任务与验证状态、相关 memory 和本规范；没有当前 PR 时检查自己的在制 PR。
简报当前状态与第一个可执行项，在既有授权内直接继续。没有在制 PR 时按授权计划 / 目标选下一项；
目标缺失或有未决取舍才询问，不接管同账号下其他会话的 PR。

## 越界防护

**是否询问取决于目标与决策边界，不取决于文件数、报错或工作量。**

| 自主处理并更新 PR | 需要 User 裁决或补充输入 |
|---|---|
| 为已授权目标补充必要文件、调用点、测试与文档，更新 Scope / 任务 | 扩展到新需求、子系统目标，改变已确认的行为 / 架构 |
| 自动解决冲突、修复本次引入或同步 main 暴露的相关失败 | 设计无法兼容，现有规范与授权不足以确定取舍 |
| 算法、内部数据结构、变量命名与既有契约内的措辞 | 未授权的对外接口、语义或性能取舍，完成条件有实质歧义 |
| 普通返工、估时变化、既有规范可确定的前置适配 | 缺少必要权限 / 输入，或有未授权的外部影响 |

Scope 清单不阻挡必要的根因修复，也不能借更新清单扩张目标。独立问题另记，目标覆盖时另开 PR。
force-push、删他人分支等未授权动作需确认；本轮合并与清理的默认授权见阶段 6。
需要询问时说明证据、选项与推荐，并继续不依赖该决策的工作。

## 测试要求（必须遵守）

**功能与修复必须有对应测试；纯重构复用有效覆盖，纯文档 / 纯注释无需新增代码测试。**

| 变更类型 | 测试要求 |
|---------|---------|
| 新功能 / 新 pipeline 阶段 | 至少 1 个正常用例 + 1 个边界 / 异常用例的单元测试或 golden test |
| Bug fix | 至少 1 个回归测试，覆盖修复的 bug 场景 |
| 新 IR 指令 / VM 行为 | golden test (run/) 验证端到端执行结果 |
| 新 CLI 命令 / 工程文件字段 | 单元测试验证解析正确性 + 错误输入报错 |
| 性能优化（`perf`） | 被优化的路径必须有 bench 覆盖：已有 e2e scenario / `[Benchmark]` 覆盖 → 附同 runner A/B 结论；没有 → 同一 PR 补一条（怎么加、怎么判红见[性能基准与回归门禁](../../internals/src/devinfra/benchmarking.md)）。**PR 描述必须记录优化前后的数据**（scenario × mode 的 base/pr 均值与结论）——证据进 PR 描述，不进源码注释 |
| refactor | 确保已有测试仍覆盖（不必新增，但不得删除测试） |

用例放哪（「被测对象在哪，测试就在哪」）见[怎么跑测试 · 用例放哪](../../internals/src/devinfra/testing.md)。
