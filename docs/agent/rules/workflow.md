# z42 人机协作工作流（以 Pull Request 为单位）

> 不依赖任何外部工具：状态存在 git 与 GitHub PR 里。

---

## 核心模型

**一次迭代 = 一个 PR。PR 描述是这次变更的合同与记录**——开工前是方案（User 审批的对象），实施中是进度，
合并后是永久档案。方案、设计、任务清单就是它的几个小节，不另立文档。

```
Think First → Plan in PR → Build → Verify → Merge
  探索思考  → 方案写进 PR → 写代码 →  验证  →  合并
```

| 角色 | 职责 |
|------|------|
| **User** | 定方向、审批 PR 描述里的方案、裁决分歧 |
| **PR 描述** | 这次变更的人机合同，实现的唯一依据；合并后即档案 |
| **三本书** | 长期规范：用户能看见的规则落 `docs/reference/`，实现机制与决策落 `docs/internals/`（判据见 [doc-system 三问](doc-system.md)） |
| **AI** | 自驱执行各阶段；不超 Scope；不猜测歧义 |

**User 介入点只有两个：** ① 尚未授权的方案审批；② 无法依据既有目标和规范裁决的方案分歧。
已在对话或 PR 中明确授权的内容写回 PR 描述即可，不重复索要确认；直接实施类变更不另设审批。

**PR 是过程的家，不是知识的家。** 凡改变了对外行为或内部机制的，知识必须在**同一个 PR 内**上浮进三本书对应页；
PR 描述只记「这次为什么这么做、做了什么、验证了什么」。要查某特性为何如此：`git log -S<符号>` 找到提交，
提交标题带 `(#N)`，`gh pr view N` 看当时的方案与决策。

**源码注释也不是过程记录的家。** profile 数据、测量日期、热点归因、A/B 前后数字这类**一次性证据**只进
PR 描述，不写进源码注释；源码注释只写代码本身表达不了的东西——不变量、等价性前提、并发安全边界、
维护陷阱（「两处须同步改」）。判据：这条注释陈述的是代码的持久事实，还是某次测量的快照？快照进 PR，事实留注释。
**来源标注同理**：`(epic, 2026-MM-DD)` 式日期戳一律不写——分支 / epic 名可留作指针，时间维度由 git 历史
与 PR 承载；归档文档**路径**与生成器产出的文件头横幅里的日期是名字本体，不在此列。**「实测」作为陷阱
警告的验证标记保留**；一次性数字（耗时 / 占比 / 计数）非陷阱本体则不写，只留结论。**叙事块整删**：
立门故事（「立门时我先写成…」）、事故回放（「#N 那次…」逐轮枚举）、迁移考古（「folded from the former
scripts/X」「收敛自两份拷贝」）不写进注释——它们的结论若仍成立，压成一句判则留下；故事本体进 PR 描述
或门禁的文档页。

## 持续迭代与持续发起 PR

**User 要求「持续迭代」「持续发起 PR」「自动推进」时，在其指定目标与范围内持续执行，不能把开出一个 PR 当作任务完成。**

1. **确定边界**：从 User 指令记录目标、范围与完成条件；固定 PR 清单按阶段 3 批量授权执行，
   开放式迭代则按目标选择下一项，不要求提前列尽所有 PR。没有指定的方向不自行扩张。
2. **逐轮交付**：检查当前实现、测试和已有 PR，优先处理范围内有证据、可验证的缺口；每轮一个逻辑单元，
   在独立 worktree 实施、验证、发起 PR，并持续处理自己的 PR 的审查反馈、CI 失败和合并冲突。
   同一项后续修正更新原 PR，不重复开 PR；有价值的独立改动才进入下一轮，不为空转凑 PR。
3. **冲突自动解决**：按阶段 6 的冲突处理与合并门禁自行解决、验证、推送；需要 User 裁决的边界统一见[越界防护](#越界防护)。
4. **接续推进**：达到阶段 6 的合并条件就自动合并、清理，再基于最新 main 开始下一轮并发起下一 PR。
   当前 PR 等 CI 或审查时，可推进不依赖它的下一项；保留对未完成 PR 的跟进，不把阻塞藏进新 PR。
   每轮汇报 PR 链接、验证结果和下一步，无需等待 User 回复「继续」。
5. **结束或交接**：目标完成、User 要求暂停，或遇到无法自主排除的外部阻塞 / 未授权决策时，说明当前状态与原因。
   开放式目标范围内已无有价值的可执行项时，报告检查结果；需要中断且仍有后续工作时按阶段 6 保存交接信息。

持续迭代授权不降低 Spec-First、测试、文档同步与合并门禁；未获授权的新语义仍走完整模式审批。

## PR 即在制品账本

| 要知道什么 | 看哪里 |
|-----------|-------|
| 现在有哪些变更在做 | `gh pr list`（含 draft）；别人的 PR 不碰 |
| 某个变更做到哪了 | 该 PR 描述里的任务清单（勾选框） |
| 某个变更方案是什么、User 批没批 | 该 PR 描述 + User 的确认（评论或对话中的明确肯定） |
| 过去某个变更为什么这么做 | `git log -S` → `(#N)` → PR 描述；长期结论已上浮到三本书 |

**命名**：分支用 kebab-case、动词开头、≤ 5 词（`add-for-loop`、`fix-type-check-crash`）；PR 标题用
`type(scope): 描述`（见 [commit-log.md](commit-log.md)）。

## 变更分类

| 类型 | 触发条件 | 模式 |
|------|---------|------|
| `lang` | 新语法、关键字、类型规则 | **完整模式**（阶段 0–6） |
| `ir` | 新 IR 指令、zbc 格式变更 | 完整模式 |
| `vm` | VM 执行语义变更 | 完整模式 |
| `fix` | Bug 修复，不改语义 | **最小模式**（PR 描述写变更说明 + 任务） |
| `refactor` | 纯重构，不改行为 | 最小模式 |
| `test/docs` | 测试或文档 | 直接实施，PR 描述写 What / Why 即可 |

**判断规则：类型优先，文件数作为 fix / refactor 内部细分。**
- `lang` / `ir` / `vm`：**无论文件数量**，一律完整模式
- `fix` / `refactor`：> 3 个文件 → 最小模式（带任务清单）；1–3 个文件 → 直接实施；单行 bugfix → 直接修改

**词汇警报**：检测到「新语法 / 新关键字 / 新 IR 指令 / 新约束 / 新接口契约 / 新类型规则 / 新 VM 行为」时，
**不论用户用什么语气**（即便说「快速开始」「直接做」），都走完整模式，不得降级。拿不准变更类型 → 按完整模式走：
多写几段 PR 描述的代价远小于跳过方案造成的返工和边界漂移。

## 🔴 Spec-First Self-Check（lang / ir / vm 强制）

**在写第一行实现代码之前，必须通过：**

```
[ ] 已开 draft PR，描述含 Why / What / Spec 场景 / Design / Scope / 任务清单（见阶段 2 模板）
[ ] 方案已获授权并记录在描述中（当前确认，或既有明确授权；见阶段 3）
```

**任一未达成 → 停，回到阶段 1–2 补齐，不得推进代码。**

**常见反例（皆为违规）**：
- ❌ 只有三本书里的对应页（长期规范）就开工 → 长期规范 ≠ 这次变更的方案，两者都要有
- ❌ 「迭代中和 User 逐步沟通过方案，所以 PR 描述从简」→ User 审批的是**写在 PR 描述里的文字**，不是聊天记录；
  对话里定下的内容必须写回描述
- ❌ lang / ir / vm 只写任务清单就开工（那是 fix / refactor 才允许的最小模式）
- ❌ 写完代码再补方案 → 方案的作用是在实施前定义边界，事后补齐只剩记录价值、失去约束价值

## 阶段 0：意图识别

**每次新对话首条消息触发：** 读取你所用工具的跨会话记忆（下文统称 memory，**不入库**；放在哪由各工具入口文件交代）、
当前阶段（`docs/roadmap.md`）和进行中的 PR（`gh pr list`），主动汇报状态和下一步，再处理用户输入。

读到以下关键词时触发对应动作：

| 用户说 | 做 |
|--------|----|
| 「我想做 X」/「实现 Y」 | 阶段 1（探索） |
| 「继续」/「下一步」 | [会话恢复协议](#会话恢复协议) |
| 「直接做」/「快速开始」 | 最小模式（**仅 fix / refactor 适用**；词汇警报优先） |
| 「开始写代码」/「实施」 | 阶段 4（须先通过阶段 3） |
| 「没问题」/「可以开始」 | 阶段 3 通过 → 阶段 4 |
| 「批量确认」/「一并授权」/「这一系列都按计划做」 | 阶段 3 批量授权模式 |
| 「持续迭代」/「持续发起 PR」/「自动推进」 | 按[持续迭代](#持续迭代与持续发起-pr)在指定目标内推进 |
| 「停」/「暂停」/「不要继续」 | 停止自动推进，保存未完成工作的状态 |
| 「验证一下」 | 阶段 5 |
| 「合并」/「完成了」 | 阶段 6 |
| 「分析一下」/「探索」 | 阶段 1，不创建任何东西 |

## 阶段 1：探索（Explore）

输出，不创建 PR / 分支 / 文件：

1. 按[开工导航](../README.md#开工先找-readme-和书)先读目录 README 与书里的对应页，再读源文件，理解现有结构
2. 梳理核心问题 / 需求
3. 列出潜在风险和边界情况
4. 提出 2–3 个可行方案（如有），给出推荐及理由
5. 存在未授权的方向 / 行为取舍时等 User 选择；目标和方案已明确或属于直接实施类时，自主选定并进阶段 2

**z42 专项检查：** 确认属于 `docs/roadmap.md` 的哪个阶段，未到的阶段特性拒绝推进；确认影响的 pipeline 组件
（Lexer / Parser / TypeChecker / Codegen / VM interp / JIT）；`gh pr list` 看有没有 in-flight 的 PR 改同一批文件。

## 阶段 2：开工——分支、worktree、PR 描述

> **隔离铁律（必须遵守）：每一次改动都在自己专属的 worktree 里做，一 change 一 worktree 一分支；绝不共用
> 分支 / worktree、绝不在主树上直接改——没有「改动很小可以直推 main」的例外。** 主树只作 seed 供体与
> `origin/main` 参照，不承载在制品。理由：① 主树常被并发会话共享，在其上改动会互相踩踏；② 共用分支会让
> 两条独立改动的历史 / GREEN 互相污染，无法按 PR 先来后到独立合并。worktree 把并行流物理隔离，git 负责
> 文本冲突，GREEN gate 负责语义正确。

1. **建 worktree**：先 `git fetch`，基于**最新 `origin/main`**（别基于滞后的本地 ref）开同名分支——
   `git worktree add -b <branch> ../wt/<branch> origin/main`；分支命名见[「PR 即在制品账本」](#pr-即在制品账本)。
   **供种后必须按当前源码重建 `xtask`**——门禁逻辑本身编在 `xtask.zpkg` 里，拿供体树那份旧的去查本树的
   新文档 / 新测试 = **保证假红**。命令见[开发环境 · 并行 worktree 供种](../../internals/src/devinfra/dev-setup.md)。
2. **完整模式：先开 draft PR，再写代码。** PR 需要至少一个提交，用空提交承载（squash 合并时它会消失）：
   ```bash
   git commit --allow-empty -m "chore: 开工 <name>"
   git push -u origin <branch>
   gh pr create --draft --title "type(scope): 描述" --body-file <描述文件>
   ```
   **最小模式 / 直接实施**：实施完成、GREEN 后再开 PR（描述按下面对应模板）。
3. **把方案写进 PR 描述**（已有授权写明依据；尚未授权的取舍按阶段 3 请 User 审阅）：

**完整模式模板（lang / ir / vm）：**

```markdown
## Why
[1–3 句：背景和问题，不做会怎样]

## What Changes
- [变更点列表]

## Spec（可验证场景）
### <Capability 名>
- **WHEN** <触发条件> **THEN** <预期结果>        # 正常场景
- **WHEN** <条件> **THEN** <结果>                  # 边界 / 异常场景
修改现有行为时写 **Before / After**。
lang / ir 类必含：**IR Mapping**（新语法对应的 IR 指令 / zbc opcode）+ **Pipeline Steps**
（受影响阶段勾选：Lexer / Parser·AST / TypeChecker / IR Codegen / VM interp）。

## Design
- **Architecture**：[ASCII 图或组件关系]
- **Decisions**：每条写「问题 / 选项 A·B 的优缺 / 决定与理由」
- **Testing Strategy**：单元测试 / golden test / VM 验证（`xtask test` 完整 GREEN）

## Scope（目标边界与本轮文件清单）
[已授权目标与完成条件]
| 文件路径 | 类型 | 说明 |
|---------|------|------|
| `src/path/Foo.z42` | NEW / MODIFY / DELETE / RENAME | … |
只读引用（理解上下文必须读但不改）：`src/path/Existing.z42` — 用于理解 X

## Out of Scope / Deferred
- [明确排除项；延后项另按 philosophy.md「延后特性管理」登记]

## Open Questions
- [ ] [待确认问题]

## 任务
- [ ] 1.1 [具体任务，指定文件和方法]
- [ ] 2.1 …（按 pipeline 顺序：Lexer → Parser/AST → TypeChecker → Codegen → VM interp → 测试 → 文档）

## 验证
base: <本轮 GREEN 基于的 main sha>
[阶段 5 的验证结论]
```

**最小模式模板（fix / refactor）：**

```markdown
## What / Why
**变更说明：** [一句话]　**原因：** [一句话]
**文档影响：** [需要更新的文档；无则写「无」]

## 任务                       # fix/refactor > 3 文件时必写；≤ 3 文件省略
- [ ] 1.1 [任务]
- [ ] 1.x 文档同步（若有行为 / 机制变更，按 doc-system 三问）

## 验证
base: <sha>
[GREEN 状态]
```

**Scope 表的两条硬性约束（完整模式必备，最小模式建议）：**
- 必须是项目内可解析的**具体文件路径**，不允许 `src/compiler/*` 通配，也不允许「相关测试文件」这种模糊描述
- 每条 NEW / MODIFY / DELETE 必须能被至少一项任务命中；反过来，任务触及的所有文件必须**全部**列入 Scope

> 实施中补充文件清单或需要扩展目标时，按[越界防护](#越界防护)区分处置。

**并行冲突**：开工前 `gh pr list` 看是否有 in-flight PR 改同一文件 / 子系统。**不预先串行、不排队**：先就绪的先合，
文本冲突在同步 main 时暴露，语义冲突由合并前的完整 GREEN 兜底（见[阶段 6「并行与合并顺序」](#并行与合并顺序多-pr-in-flight)）。
明显深度耦合的（如都在动 GC safepoint 语义），在两边 PR 描述里互相知会。

## 阶段 3：实施前确认（Gate）

### 单 PR 模式（默认）

- **直接实施 / 最小模式**：User 已要求完成该变更即可实施，不额外等待一次「开始」。
- **完整模式**：先把 Why / Spec / Design / Scope / 任务写进 draft PR。已有明确授权覆盖这些决策时，
  记录授权依据并继续；存在尚未授权的行为或架构取舍时，展示 PR 链接、方案摘要和待裁决点，确认后实施。
- User 提出修改时先更新描述；只有修改引入新的未授权取舍才重新确认，不逐节、逐次提交索要批准。

### 批量授权模式（Batch Approval）

**触发**：User 明确授权一组 PR 或计划（如「这一系列都按计划做」「一并授权」）。

1. 把目标、PR 清单、依赖与授权依据记录到各 PR 描述；此前已确认的计划不再问一次。
2. 按依赖逐个实施 → 验证 → 合并，每轮汇报落地结果并自动开始下一项。
3. 每个 PR 独立成一个逻辑单元、通过 GREEN、同步文档；是否需要停下统一按[越界防护](#越界防护)判断。

**边界：** 固定清单只授权该组 PR；User 同时要求持续迭代时，后续选题按[持续迭代](#持续迭代与持续发起-pr)的目标边界执行。
授权覆盖范围内的实施、commit、push、开 PR、合并及清理自己的已合并分支 / worktree；
force-push、删他人分支及其他未授权的外部影响动作需单独确认。CI 配置是否可改取决于授权目标，不能仅因文件类型要求再次确认。
User 要求暂停时立即停止自动推进。

## 阶段 4：实施（Apply）

对每个任务：
1. 宣告「正在处理 N.M: [描述]」
2. 读取相关文件，实施代码变更
3. 把 PR 描述任务清单里对应项 `[ ]` → `[x]`（`gh pr edit --body-file`；允许在 push 时批量更新，不必逐项）
4. 简短说明完成情况；遇到阻塞 → 写进 PR 描述并告知 User

**任务粒度：** 每项对应一个可验证的结果；不为凑时长拆出没有独立意义的步骤。

**z42 pipeline 顺序（不跳步）：** Lexer → Parser → AST → TypeChecker → Codegen → VM interp → 测试

**与方案偏差时：** 先按[越界防护](#越界防护)判断。范围内的实现调整写回 PR 描述并继续；改变目标或未授权的行为 / 架构取舍才请 User 裁决。

**实施过程中的验证要求：**
- 每个 refactor / fix / feature 实施后，立即在本地运行编译 + 测试
- 测试失败的处置按阶段 5 的[测试失败处理表](#阶段-5验证verify)，不在本阶段另立口径
- 不得跳过任何测试失败继续下一个任务；整个阶段 4 完成后，进阶段 5 前必须全绿

## 阶段 5：验证（Verify）

**全绿（GREEN）标准**——进阶段 6 前必须通过全部验证，且**所有测试全部通过**。统一入口：

```bash
cargo build && xtask test          # 默认串联所有必跑 stage（完整 GREEN gate）
```

- **dev 期可以缩窄**（`xtask test changed` / 单 stage / `--no-build`），但 **commit 前最终 GREEN 必须跑完整
  `xtask test`**——partial 验证只算快速迭代，不替代门禁。
- **stage 清单不在这里复列**：见 [GREEN gate](../../internals/src/devinfra/test-gate.md)（`xtask test --list` 查询执行清单）。单跑某层、按改动挑 stage、「我改了 X 该验什么」见
  [怎么跑测试](../../internals/src/devinfra/testing.md)。
- 发行版变更（xtask package / 跨平台 / 嵌入接口）追加跑 `xtask package sdk --verify`。

**测试失败处理（唯一口径）：**

| 情况 | 处理方式 |
|------|---------|
| 当前变更导致的新失败 | ❌ 必须在本迭代修复，不得 commit |
| 当前变更触发的隐藏 bug | ❌ 必须修复，或明确说明理由后 User 确认 |
| Pre-existing 失败（变更前已存在） | ⚠️ 必须在**同一迭代**修复，或单独 issue 跟踪 |
| 问题与当前 Scope 无关 | 记入 PR 描述 Out of Scope，按授权范围另开 PR / issue；相关门禁仍红时不得合并 |

**验证报告（写进 PR 描述的「验证」段，并在对话中输出）：**

```markdown
## 验证
base: <本轮 GREEN 基于的 main sha>
xtask test：✅ 全绿（N stages）/ ❌ 失败 at <stage>      # 全绿时一行即可，失败才逐 stage 展开
Spec 覆盖：| 场景 | 实现位置 | 验证方式 | ✅ |             # 完整模式
任务：N/N ✅
结论：✅ 可合并 / ❌ 未全绿，待修复：[列出]
```

**全绿才能进阶段 6。** 未全绿不得最终提交 / 标 ready / 合并；草稿 PR 可推送过程提交用于协作与 CI 定位，但须明确标记未完成。

## 阶段 6：合并（Merge）

> **铁律：文档同步与方案定稿都在 PR 内完成，合并后只做清理，不补内容。** 禁止「代码先合、文档后补」，
> 禁止合并后再单独推一个文档提交到 main。

1. **文档同步**：判据是 **[doc-system.md 的三问](doc-system.md)**（唯一 SoT，落点与「三问全否」的处置都在
   那里，本阶段不复列）——逐问过一遍，命中的按该处落点更新。另有三处与三问正交、命中就得改：根 `README.md`
   （影响仓库门面时）、`docs/roadmap.md`（延后项被消化 / 新增，或阶段进度变化时）、`docs/agent/rules/`
   （改的是协作规则 / 流程本身时）。**合并前 doc-check 清单**见
   [doc-system.md「三道门」](doc-system.md)的门③，不在此复列。
2. **PR 描述定稿**：把描述更新成**最终状态**——实施中偏离方案的决策、实际 Scope、产生的 Deferred 项、验证结论。
   合并后它就是档案，不再改写。
3. **提交**（无需 User 确认）：`git add <本变更 Scope 内的路径>`（不是 `git add -A`），`git commit -m "type(scope): 描述"`；
   每个逻辑单元单独提交（判据见 [commit-log.md](commit-log.md)）。
4. **落地到 main**——**合并前置：必须先把 main 最新改动并进来并重跑完整 GREEN，全绿才能合。**
   未发布的分支可 rebase；已发布的 PR 分支默认 merge `origin/main`，以普通 push 同步，避免改写远程历史。
   ```bash
   git fetch origin
   git merge --no-edit origin/main
   # 有冲突时先解决，再 git add <冲突文件> && git commit --no-edit
   xtask test                               # 基于最新 main 完整验证；base sha 写进描述
   git push origin <branch>                 # 同步合入 main 与冲突修复后的最终提交
   gh pr ready                              # 仅 draft PR 需要
   gh pr merge --squash --delete-branch --match-head-commit <已验证的head-sha>
   ```
   **PR 冲突不是暂停理由**：文本冲突、文件移动、编号碰撞、可由已授权方案 / 现有规范确定的语义适配均自行处理；
   保留双方仍有效的意图，修复调用点与测试，不整片选 ours / theirs 丢弃另一方改动。
   冲突消除后运行相关回归与完整 GREEN，再推送并跟进 CI。
   确有未授权的方案分歧才按[越界防护](#越界防护)询问。force-push 不属于默认冲突处理方式。
   **最终提交必须与验证一致**：检查远端 PR head 为本轮验证的提交、所需 CI / 审查已通过，
   且 main 未前进；否则重新同步、验证、推送，再检查合并条件。不得绕过保护规则或用旧 head 的 CI 代替当前结果。
   **squash 提交正文**写 Why + What 摘要（≤ 10 行）和关键决策；完整方案留在 PR 描述，靠提交标题的 `(#N)` 找回。
5. **合并后清理（必做，默认授权）**：删该 change 的远程 + 本地分支 + worktree，不留残枝。
   ```bash
   git worktree remove <worktree-path>      # 有未提交改动时会拒绝——先确认没漏东西
   git branch -d <branch>                   # 本地分支
   git push origin --delete <branch>        # 远程分支（用 --delete-branch 合并时已删）
   ```
   删自己这条已合并 PR 的分支 / worktree 属**默认授权**；force-push / 删他人分支仍需单独确认（阶段 3 边界）。
6. **继续或交接**：仍有已授权后续任务时，按[持续迭代](#持续迭代与持续发起-pr)直接进入下一轮，
   不以续推口令代替执行。只有需要中断且仍有未完成工作时，才保存 memory（不入库）：
   目标与授权边界、已落地 PR 和关键决策、未完成任务 / 阻塞、worktree 与种子位置、验证结果和下一步。
   给出一句无歧义的续推口令，让新会话能凭 memory 与所链 PR 接手；没有后续任务时无需口令。

### 并行与合并顺序（多 PR in-flight）

- **先来后到，不排队**：谁先 GREEN + 就绪谁先合，无需声明占用。改不同子系统的天然无关、各自合；改同一子系统
  甚至同一文件的，文本冲突在同步 main 时暴露、语义冲突由「并入 main + 重跑完整 GREEN」兜底——**不预先串行、不排队**，
  让先就绪的先合，后者同步最新 main 后再跑。
- **GREEN 结论会过期**：「绿了」不是一个属性，而是对**某个 main sha** 的断言——main 一动断言就可能失效，而绿灯
  不会自己熄灭。合并前若 main 已前进到你跑 GREEN 的 sha 之外，**必须重跑再合**；PR 描述里写明本轮 GREEN 基于哪个
  sha，否则审阅者无从判断那个绿灯还算不算数。验证与按下 merge 之间的窗口里落地的 PR 会让结论过期。
- **本地 GREEN 可能被热产物掩盖**：夹具产物缓存命中就不重编，编译错误可能只在冷构建出现 ⇒ 改动会影响编译产物时
  （编译器 / 清单解析 / 发现规则），合并前至少跑一轮**冷**的（命令见[怎么跑测试](../../internals/src/devinfra/testing.md)
  「冷跑一轮」）。与上一条同一个形状：**绿灯的前提变了（base sha 或产物状态），绿灯却不会自己失效**。
- **语义耦合的代价要认清**：worktree + PR 解决物理隔离与文本冲突，**解决不了语义耦合**——两个 PR 改 `runtime`
  的不同文件、行不重叠、各自 clean merge，合起来逻辑却可能坏，git 测不出来（高发区：GC / JIT / safepoint 边界，
  以及共享基础设施文件）。兜底就是上面那条同步 main + 完整 GREEN。**这是用「返工换并行度」的权衡**——把返工推到
  合并前就地修，而不是「冲突消失了」；pre-1.0 快速迭代期通常值。明显深度耦合的两个 change，开工前在 PR 描述里
  互相知会一声能省一轮返工（建议，非强制）。
- **改「跑测试的工具」时，它依赖的源码修复必须先落地**：变更让 gate 用更严格的方式编译 / 运行既有源码时
  （如 `bench-regression` 用 PR 的 runner 跑 base 树），配套源码修复必须是**独立的、先合并的** PR——否则 base 树
  缺那条修复，新 runner 一编就红。本地 GREEN 测不出这一类（本地不会拿新工具跑旧树）。
- **抢同一个「全局唯一编号」时按合并顺序让号**（诊断码号最典型）：**先合进 main 的保留，后合的让号**——不比
  「谁先想到 / 谁改动小」，合并顺序是 git 里的客观事实。占号必须落在唯一的登记表里（抢号才会变成文本冲突）。
  诊断码流程以[错误码全表](../../reference/src/appendix/error-codes.md)「新增一个码」为唯一 SoT。CI 的 diagcodes
  复查只覆盖码号一维且有窗口，**不替代** 同步 main + 完整 GREEN。

## 会话恢复协议

User 说「继续」时，自动执行：

1. `gh pr list --author @me`（含 draft）与当前分支对应的 PR（`gh pr view`）
2. 读该 PR 描述的任务清单，找到第一个未勾选任务
3. 读 [docs/agent/README.md](../README.md) → 规范索引与当前阶段约束；读 memory → 跨会话决策
4. 简短汇报当前 PR、已完成项、下一步；既有授权仍有效时直接继续，不再问「继续？」。
5. 无进行中 PR 时，按已授权计划或持续迭代目标选择下一项；缺少目标 / 授权或存在未决取舍才询问。

## 越界防护

**是否询问取决于目标与决策边界，不取决于文件数、报错或工作量。**

| 自主处理并更新 PR 描述 | 必须询问 User |
|---|---|
| 为实现已授权目标补充必要文件、调用点、测试与文档，更新 Scope / 任务 | 扩展到新的需求、子系统目标，或需要改变已确认的行为 / 架构 |
| 自动处理 PR 冲突、修复本次引入或因同步 main 暴露的相关失败，重新验证 | 双方设计无法兼容，且现有规范与授权不足以确定取舍 |
| 算法、内部数据结构、变量命名、已有契约内的措辞等实现细节 | 新的对外接口 / 语义 / 性能取舍不在授权内，或完成条件存在实质歧义 |
| 普通返工与估时变化、已有规范可以确定的前置适配 | 需要不可逆操作、未授权的外部影响动作，或缺少必要权限 / 输入 |

Scope 表记录本轮实际改动，不能用文件清单遗漏阻挡必要的根因修复，也不能借更新清单扩张目标。
范围外的独立问题记入 PR 描述；持续迭代目标覆盖它时另开 PR，否则只记录，不顺手混入当前 PR。
测试失败按阶段 5 处理，失败本身不触发重新授权，未全绿仍不得合并。
发现需要询问的阻塞时，说明证据、选项和推荐，并继续不依赖该裁决的已授权工作。

## 测试要求（必须遵守）

**每次新增需求或迭代（非纯文档 / 纯注释变更），必须包含对应的测试用例。无测试 = 未完成。**

| 变更类型 | 测试要求 |
|---------|---------|
| 新功能 / 新 pipeline 阶段 | 至少 1 个正常用例 + 1 个边界 / 异常用例的单元测试或 golden test |
| Bug fix | 至少 1 个回归测试，覆盖修复的 bug 场景 |
| 新 IR 指令 / VM 行为 | golden test (run/) 验证端到端执行结果 |
| 新 CLI 命令 / 工程文件字段 | 单元测试验证解析正确性 + 错误输入报错 |
| 性能优化（`perf`） | 被优化的路径必须有 bench 覆盖：已有 e2e scenario / `[Benchmark]` 覆盖 → 附同 runner A/B 结论；没有 → 同一 PR 补一条（怎么加、怎么判红见[性能基准与回归门禁](../../internals/src/devinfra/benchmarking.md)）。**PR 描述必须记录优化前后的数据**（scenario × mode 的 base/pr 均值与结论）——证据进 PR 描述，不进源码注释 |
| refactor | 确保已有测试仍覆盖（不必新增，但不得删除测试） |

用例放哪（「被测对象在哪，测试就在哪」）见[怎么跑测试 · 用例放哪](../../internals/src/devinfra/testing.md)。
