# z42b：构建编排器

> 对齐：2026-09-17（change `restructure-docs-three-books`）｜ 代码：`src/toolchain/builder/core/`、`src/libraries/z42.build/src/`
>
> 命令与旗标怎么敲 → [工具链参考](../../../reference/src/toolchain/README.md)；清单字段 → [`z42.toml` 参考](../../../reference/src/toolchain/z42-toml.md)。

`z42b` 是工具链里负责**编排**的那个进程：读工程清单与目标 RID，装配一条固定阶段的构建管线，
把编译交给 z42c、把平台收尾交给 workload，自己只做装配与调度。它同时是 `[Test]` / `[Benchmark]`
的反射式运行器，以及 desktop 的发布实现。**改构建流程、加构建扩展点、查「publish 到底做了什么」
时读这页。**

## 定位与进入方式

z42b 是一个普通的 z42 程序：`src/toolchain/builder/core/*.z42` 编成 `z42.builder.zpkg`，
随 SDK 落在 `programs/z42b/`，配一个 native apphost `bin/z42b`（同 launcher 的
「源 → zpkg → apphost」形状）。

两条进入路径：

| 谁调 | 怎么调 | 动词 |
|---|---|---|
| launcher | `z42vm programs/z42b/z42.builder.zpkg -- <argv>`（`_forwardZ42b`） | `new` / `test` / `bench` / `clean` / `publish` |
| 编排方（xtask、CI） | 直接跑 `bin/z42b` 或上面那条命令 | 另加 `build` / `export` |

`z42 build` **不**到 z42b —— launcher 直接转发给 `bin/z42c`。z42b 的 `build` 动词是给编排方走
in-process 编译路径用的，两者产物布局一致但代码路径不同。

## 管线：九个阶段

阶段名是封闭常量集（`Z42.Build.Phase`），线性、不可增删改序；所有定制只能落在 hooks 与
workload 的 override 上。这样阶段序列本身可以被当成确定量来做缓存与推理。

```
head（z42.build 拥有，平台无关）      tail（workload 拥有，虚分发沿继承链）
Resolve → Preflight → Compile → Trim → Assets → Configure → GenerateProject → NativeBuild → Package
                                                                     ▲                          ▲
                                                             export 停在这之后            publish 跑到这
```

`Preflight` 虽然由 workload 实现，却夹在 head 里、排在 `Compile` 之前——
平台工具链缺失要 fail-fast，不能等编译完几十秒再报「没装 Xcode」。

| 阶段 | 契约 | 当前实现 |
|---|---|---|
| `Resolve` | 解析依赖、按 RID 激活 workload | 空方法体 |
| `Preflight` | 工具/依赖检查与下载（fail-fast） | `WorkloadBase` no-op |
| `Compile` | 源码 → `app.zpkg` | **唯一有实现的阶段**，见下 |
| `Trim` | 从 entry 可达性裁剪 zpkg | 空方法体 |
| `Assets` | 收集 zpkg + stdlib + runtime 到暂存 | 空方法体 |
| `Configure` | 应用平台身份（包名/签名/能力） | no-op |
| `GenerateProject` | 生成原生工程；export 停点 | no-op |
| `NativeBuild` | 调宿主工具链构建 | no-op |
| `Package` | 产出最终交付物 | no-op |

**tail 四阶段今天全是空的**：`_selectWorkload()` 无条件返回基类 `WorkloadBase`，
`iOSWorkload` / `AndroidWorkload` / `WasmWorkload` / `DesktopWorkload`
（`src/toolchain/workload/*/appbuilder/`）虽然按 `: WorkloadBase` 写好了类型骨架，方法体却只有
流程注释，且没有任何代码把它们接进 `_selectWorkload`。真正在跑的平台逻辑不在管线里，
见下面「管线之外的两条实路」。

Pipeline 之外还有一步：`_buildProject`（`builder_commands.z42`）在 `Pipeline.Run` 返回后，
把 `Intermediate/app.zpkg` 拷成 `dist/<name>.zpkg` 并调 `_pubBundleProjectDeps` 把 path 依赖
平铺进 dist。即「产物落位」这件事目前住在命令层，不在 `Assets` 阶段。

## 编译：`ICompiler` 与运行时注入

`Compile` 阶段经 `z42.build` 定义的 `ICompiler` 接口调编译器，**在同一个 VM 进程内**，
返回类型化的 `CompileResult` 而不是解析 stdout。

```
ICompiler（z42.build 定义，只有接口）
   ├─ z42c.driver CLI          → 自己构造 CompileRequest → Compile()
   └─ z42b Pipeline.Compile    → 从 ctx 构造 CompileRequest → Compile()
```

依赖方向是倒置的：`z42.build` 只持接口，实现 `Z42.Pipeline.Z42cCompiler` 住编译器侧
（`src/compiler/z42c.pipeline/`），于是 `z42c → z42.build`、`z42b → z42.build`，无环。

**但 z42b 连编译期都不依赖 z42c**：`_hostCompiler()` 走运行时动态注入三段式——

1. `_findCompilerZpkg()` 定位 `z42c.pipeline.zpkg`，探测序
   ① `$Z42_HOME/programs/z42c/` ② `$Z42_PORTABLE_VM` 反推的 SDK 根 ③ 开发树
   `artifacts/build/compiler/z42c.driver/release/dist/`；
2. `ModuleLoader.Load(zpkg)` → `Type.GetType("Z42.Pipeline.Z42cCompiler")` → `Activator.CreateInstance`；
3. `as ICompiler`，失败（组件缺失 / 类型不可解析 / 接口版本不匹配 / 抛异常）一律退回 `NoCompiler`，
   打一条诊断而不是崩。

这条约束不是洁癖：z42b **兼作 stdlib 自己的测试运行器**，而 stdlib 的 `[Test]` 构建阶段
`Z42_LIBS` 里只有 stdlib —— 那时 z42c 的包根本不在场。编译期零 z42c 依赖，z42b 才能在那个上下文里
被编出来。换编译器实现 = 换 zpkg，z42b 一行不改。

`CompileRequest` 有三个字段是**构造后赋值、不进 ctor 签名**（`ParentPkg` / `Includes` /
`PackageName`）：`z42.build` 是 z42c 自己的依赖库，给既有导出类型加 ctor 参数会让上一版种子的
构造调用元数对不上，见 [自举与种子](../compiler/self-hosting.md)。

## 项目 hook：动态注入，不生成 driver

工程在清单里显式声明 hook 目录：

```toml
[build]
hooks = "hooks"          # 相对工程目录
```

hook 源固定约定 `namespace Build;` + `class ProjectHooks : BuildHooks`，override 需要的钩子。
`_loadProjectHooks`（`builder_hooks.z42`）的机制与 `_hostCompiler` 同款：

1. 把 hook 源**拷到 staging 目录**，附一个合成的 no-op `Main()` —— 编译器的目录编译面固定
   `kind=exe`，hook 目录没有 `Main` 会被判「no Main() found」；`ModuleLoader.Load` 并不执行 Main，
   这个入口纯粹是为了满足编译面；
2. 用**注入进来的同一个 `ICompiler`** 编 staging 目录 → `<proj>.hooks.zpkg`；
3. `Load` → `Type.GetType("Build.ProjectHooks")` → `Activator` → `as BuildHooks` → 挂上 `p.Hooks`。

三条设计后果值得记住：

- **hook 目录必须显式声明，不做隐式探测**。隐式探测 `build/` 会把本仓 `scripts/build/` 这类
  普通源码目录误判成 hook 目录。
- **hook 源不能被应用自己的源发现扫进去**。`Pipeline.Compile` 把 `<hooksDir>/**` 追加进
  `CompileRequest.Excludes`；否则 app 的 `**/*.z42` glob 会把 `ProjectHooks` 编成一个跨包死类，
  刷一屏 vtable fixup 假警报。
- **hook 编不过不阻塞主构建**：返回 null、打诊断、降级为无 hook。

`BuildHooks` 的扩展点：`BeforeCompile` / `AfterCompile` / `BeforeTrim` / `AfterTrim` /
`BeforeAssets` / `AfterAssets`，加一个专用窄阶段 `ProvideNative`（只负责现场编/拷本包的私有
native 库并 `ctx.AddOutput("native", …)` 登记，消费方沿 path 依赖闭包**只跑这一个**钩子，
不盲跑通用的 `BeforeAssets`）。

平台侧的对称扩展点是 `class <Plat>Build : <Plat>Workload` + `base.X(ctx)`；注入代码尚未写，
`_selectWorkload` 仍是 no-op。

## 管线之外的两条实路

设计上「一切走 Pipeline」，实现上有两条平台真逻辑绕开了它。不知道这件事就会在错误的文件里找 bug。

**① desktop publish 完全不经 Pipeline。** dispatch 把 `publish` 送到
`_cmdPublishZ42b`（`builder_publish.z42`），它自己走一遍
「gate `[platform.desktop] apphost = true` → 解析 apphost stub → 确保产物最新 → patch stub →
搬 payload 与依赖」。`builder_commands.z42` 里那个走 Pipeline 的 `_cmdPublish` **没有调用点**。

**② publish 的「确保已构建」这一步 fork z42c 子进程。** `_pubEnsureBuilt`
（`builder_publish_build.z42`）从 `$Z42_PORTABLE_VM` 反推 `<sdk>/bin/z42c`，
`Process(z42c).Arg("build").Arg(toml).Arg("--release")` 跑一遍。
即「in-process、不 fork z42c」只对 `build` / `export` / compile-then-test 成立，publish 不在其中。

这么写是有理由的：publish 每次都无条件过一遍 z42c，把「新旧判定」整个交给 z42c 的文件级内容哈希
增量缓存——工具链里只有它真的知道源码变没变。少一套判据，就少一个会跟真相跑偏的判据。
`--no-build` 是旧「就用现成字节」契约的显式化版本，留给自己已用特定编译器编好、
要求字节不被动的调用方（SDK 组装、自举不动点）。

publish 也用 hook，但同样不经 Pipeline：`_pubHookApphostStub` / `_pubRunHooks` 自己
`_loadProjectHooks` 后**只手工调一次 `BeforeAssets`**，再从手搭的 `PipelineContext` 里
收 `ctx.Outputs()`，按 `Kind` 取 `apphost-stub` / `embed-*`。

apphost stub 的解析序因此是：**① 工程 hook 现场产出 → ② `Z42_APPHOST_TEMPLATE`
（launcher 解析已装 desktop workload 后传入）→ ③ 报错并给出两条路**。
第①条正是本仓 `./xtask` 免装 desktop workload 的原因：`scripts/hooks/hooks.z42` 的 `BeforeAssets`
现场 `cargo build --release` 出 stub 并 `AddOutput("apphost-stub", …)`。
产物形态与 apphost 机制见[部署模型](deployment-model.md)。

## 边界与缺口

- **head 的 Resolve / Trim / Assets 是空的**：依赖解析实际由 `Z42_LIBS` 目录扫描
  （`_initialInputs`）顶着，裁剪没有实现，产物落位在命令层。
- **tail 四阶段没有接线**：workload 子类存在但未被选中，平台发布/导出走的是别的代码路径
  （desktop 走 `builder_publish.z42`，ios/android/wasm 走 launcher 的 export，
  见[平台发布与导出生命周期](platform-export.md)）。
- **两条编译路径并存**：in-process（ICompiler）与子进程（publish）。前者目前没有增量缓存，
  所以并行跑多个测试目标时要靠 `--reuse-parent` 避免把父包全量重编 N 遍。
- **`ICompiler` 暂住 `z42.build`**：编译器实现它就传递依赖了整个 build 框架。
  后续抽到中立微库，让编译器核心只依赖那个微库。
- **`IPipelineContext` 的 native 原语未落**：`Sign` / `Archive` / `Hash` / `ProbeVersion` /
  `Download` 仍待经 `extern` 接到 VM 侧。
