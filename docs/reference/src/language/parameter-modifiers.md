# 参数修饰符 `ref`

> 对齐：2026-09-22 ｜ 实测基准：`./.z42/z42 run`

z42 只有**一个**参数修饰符：`ref`。它让方法改到调用方的变量。

```z42
void Increment(ref int x) { x = x + 1; }

int c = 0;
Increment(ref c);     // c == 1
```

**形参和调用点都必须写**——两边不一致就报错（见[对称性](#调用点必须与形参对称)）。

## `ref` 的含义：传地址，仅此

两侧都没有附加契约：

| | |
|---|---|
| 调用方 | **不必**先赋值——槽位自动取零值 |
| 被调方 | **不必**写回 |

由此得到一条贯穿全语言的不变式：**永远不存在未初始化的存储**。
被 `ref` 取址的局部若没写初始化器，编译器在**声明处**补上该类型的零值
（`int`→0、`bool`→false、`char`→`'\0'`、引用类型→`null`、struct→按布局全零）。

```z42
int a;                // 没有初始化器
Increment(ref a);     // 合法：a 在声明处取零值 0
Assert.Equal(1, a);
```

> 零值只补给**本函数内被 `ref` 取址过**的局部。其余局部维持"未赋值即不可读"，
> 与本变更前一致。

### 适用于任何类型

引用类型同样可以 `ref`——那表示**让被调方替换调用方持有的对象**：

```z42
void FillArray(ref string[] a) { a = new string[2]; a[0] = "x"; a[1] = "y"; }

string[] xs;
FillArray(ref xs);    // xs 指向新数组
```

### 实参必须是可取址的左值

支持：局部变量 / 形参、数组元素、引用类对象的字段。

拒绝（报 [`E0470`](../appendix/error-codes.md)）：属性、索引器、blob 值 struct 的字段、
静态字段、字面量与调用结果。这四种都没有可取址的稳定存储——此前它们**编译通过但写回静默丢失**
（取的是临时寄存器的地址）。

### 嵌套透传

`ref` 参数本身可以再作为 `ref` 实参传下去，写入会一路回到最初的调用方。

## 调用点必须与形参对称

| 情形 | 结果 |
|---|---|
| 形参 `ref`，实参漏写 | `E0472` |
| 形参无 `ref`，实参多写 | `E0473` |

这两条修的是一对**方向相反**的静默缺陷。此前两边都编译通过：漏写时方法里的写入**静默丢失**；
多写时写入**却传回了调用方**——即"按引用与否由调用点决定"，光看函数声明判断不出参数会不会被改。

同时，实参与形参的类型必须**精确匹配**（基本类型别名如 `int`/`i32` 归一后视为相同），
不做隐式转换：转换会产生临时值，地址就失去了意义。

> ### ⚠️ 跨包暂不强制
>
> 跨包签名格式（TSIG）**不记录 `ref`**，导入侧拿不到修饰符信息，因此上述对称性检查
> **只在同一个包内生效**。跨包调用漏写 `ref` 目前仍然静默。
>
> 在它补上之前，**stdlib 不导出任何带 `ref` 形参的公开 API**——否则等于把这个缺口推给用户包。

## 内联声明与丢弃

```z42
if (Int32.TryParse("42", ref var n)) { … }   // 调用点声明，作用域延伸到 if 之后
if (Int32.TryParse(s, ref _))        { … }   // 不要这个出参
```

- `ref var n` / `ref int n`：在调用点声明局部并传地址，初值为零值
- `ref _`：编译器分配隐藏槽；`_` **不**进入作用域，读不到

## 多返回值

「可能没有」的结果按返回类型分流：

| 返回的是 | 写法 |
|---|---|
| 引用类型 | `V? Find(…)` —— 单个可空返回值，**不要** bool |
| 值类型 | `bool TryX(…, ref T v)` —— 失败时写零值 |

引用类型自带"缺席"的表示；值类型没有，才需要第二个通道。这样 **bool 与可空值的组合
永远不会出现**，也就不会出现"我检查了 bool、编译器还要我检查值"的双重检查。

「总是有，但是多个」用元组：`(int, string) Split(…)`。

## 参与重载

`Foo(int)` 与 `Foo(ref int)` 是**同一个签名**，同时声明报重复定义。修饰符不进入类型身份，
也不参与重载判重。

## 为什么没有 `out` 和 `in`

### `out`

它的四条规则（callee 必须全路径赋值 / 进入时不可读 / 调用后视为已赋值 / throw 路径除外）
**全部是为了处理"未初始化内存"这一个例外**。槽位自动取零值消灭了这个例外，四条规则随之消失。

人体工学由 `ref var n` 完整保留——和 `out var n` 只差一个词。

**已知代价**：被调方在某条正常返回路径上忘了写出参，不再是编译错误，调用方读到零值。
按路径分：失败路径忘写 → 调用方按约定不用那个值，无害；成功路径忘写 → 主逻辑坏掉，
任何测试都会抓到。

### `in`

它的只读保证从设计时起就是不完整的：`in` 只约束"slot 不可重赋"，**不约束指向对象的内部状态**——
`in p` 时 `p.Mutate()` 照样生效。补完需要一整套 `readonly` 成员标注系统（C# 需要
`readonly struct` + 成员级 `readonly`），而且装完之后 defensive copy 陷阱依然存在。

它的全部价值是性能（大值类型不复制），而那可以由编译器推导：**被调方的 IR 在任何路径上
都不写某个值类型形参 ⇒ 调用约定自动改为传别名**。判据是 IR 事实而非声明，因此不会声明错，
也没有 transitive hole——`p.Mutate()` 会写，优化就不做，自动退回复制，语义永远对。

> `in` 仍是 `foreach (var x in xs)` 的关键字，只是不再作参数修饰符。

## 不支持的位置

修饰符**只能用在参数上**：

| 形态 | z42 |
|---|---|
| `ref` 局部变量 `ref int x = ref expr` | 无（延后） |
| `ref` 返回类型 `ref T M()` | 无（延后） |
| `ref` 字段 | 无 |
| `ref struct` 类型 | 无——GC 语言不需要 |
| `scoped` 修饰符 | 无 |
| `ref readonly`（任何位置） | 无——由编译器推导的只读别名顶替 |

这是一条刻意的设计线：**引用永远不离开创建它的调用栈帧**，因此 z42 不需要生命周期标注。

## 运行期

`ref` 走「入口 copy-in / 出口 copy-out」：调用方发 `load_local_addr` 取址，被调方进入时
解引用得到底层值，退出前把形参寄存器的终值存回调用方的 lvalue。

这**不是**性能缺陷，是刻意的选择：

- 复制的是 `Value`（16 字节），**不是 struct blob**——blob 值 struct 在寄存器间以句柄流转，
  copy-in 拿到的是句柄，被调方直接改到调用方的 blob 上
- 对标量而言两次 16 字节复制**快于**真别名（真别名要求每次访问都间接）
- 换来的是「被调方的 80+ 条指令 handler 完全不需要感知引用」

## 错误码

| 码 | 条件 |
|---|---|
| `E0470` | `ref` 实参不是可取址的左值 |
| `E0471` | 使用了 `out` / `in` 作参数修饰符（附迁移写法） |
| `E0472` | 形参是 `ref`，实参漏写 |
| `E0473` | 形参不是 `ref`，实参多写 |
