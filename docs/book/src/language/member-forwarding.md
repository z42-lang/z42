# `[Forward]` —— 成员转发

> 用**组合**替代 z42 不支持的多继承：把一个字段的部分成员面提升到外层类型上。
> 生成的是**真方法**——只有真方法才能满足接口、被反射看见、被 IDE 跳转。

## 它解决什么

z42 只有单继承（`philosophy.md` 明文），组合是唯一替代。但组合出来的链式访问累赘：

```z42
svc._log.Log("x");        // 而不是 svc.Log("x")
```

手写转发（`public void Log(string m) => this._log.Log(m);`）是**零成本对照**——它能工作、能被
IDE 跳转、签名完全可控。`[Forward]` 要赢它，只能赢在一处：

> **上游签名面变化时，转发面自动跟上；跟不上时编译报错。**

手写转发的真实失效模式不是「写起来累」，是**上游改了签名、转发面悄悄过时**：上游把
`Log(string)` 改成 `Log(string, Level)`，手写的那份要么编译错（好），要么因为重载仍在而
**继续转发到旧重载**（坏，静默）。

## 三档粒度

三档共用**一个** attribute，由**实参形状**选档：

```z42
class Service {
    [Forward] private Logger _log;                            // ③ 配合 partial 声明
    public partial string Log(string m);                      //    用户写签名，generator 填 body

    [Forward(typeof(ILogger))] private Logger _log2;          // ① 接口面
    [Forward(methodof(Logger.Level))] private Logger _log3;   // ② 逐个点名
}
```

| 档 | 转发面由谁钉死 | 上游加重载会自动进来吗 | 签名保真 |
|---|---|---|---|
| ① `[Forward(typeof(I))]` | **接口** | 否（接口没变就没变） | 由接口签名给出 |
| ② `[Forward(methodof(X.M))]` | **逐个点名** | 否 | 见「适用边界」 |
| ③ `partial` 声明 | **你手写的声明** | 否 | ✅ 完全保真 |

**没有「public 全量省略」档**：它承担绝大部分持续复杂度换最薄收益，且「钉死名字却没钉死
签名」本身是内在矛盾——上游加重载仍会自动进转发面。

多个目标就**重复贴**：

```z42
[Forward(methodof(Logger.Log(string)))]
[Forward(methodof(Logger.Level))]
private Logger _log;
```

### 为什么白名单用 `methodof` 而不是字符串

```z42
[Forward("Log")]                             // ❌ 改名 → 静默不再转发；拼错 → 静默
[Forward(methodof(Logger.Log(string)))]      // ✅ 改名 / 签名漂 → 编译错误
```

这是 [`methodof`](methodof.md) 的第一个真实使用点。字段级 attribute 的实参**会被真正编译**，
所以 methodof 的 `E0459`/`E0460` 就是白名单的守卫。

## 语义规则

| # | 规则 | 为什么 |
|---|---|---|
| **S1** | **不产生子类型、不产生隐式转换** | `Service` **不是** `Logger`。D 语言 `alias this` 的灾难全源于此（Walter Bright：*"has turned out to be a mistake"*；DIP66 多 alias this 被 Rejected，理由「就是多继承」） |
| **S2** | `ToString` / `Equals` / `GetHashCode` / `GetType` **永不转发** | 转发身份协议会让外层对象**谎报自己是谁**。对齐 Lombok `@Delegate` 的 *"all public non-`Object` methods"* |
| **S3** | **不传递、不递归**，只提升一层 | D 的 `alias this is not transitive` 是 15 年未修的 open bug 群 |
| **S4** | 多个 `[Forward]` 提供同名成员 → **声明处**报错 | Go 推迟到用时才报，且动态接口断言处**静默返回 false** |
| **S5** | 外层已声明同名成员 → **跳过不生成** + Info 诊断 | 你的实现优先。见下 🔴 |

### 🔴 S5 不是风格选择

**跨碎片同名重载会让先声明的那个从方法表里静默消失**（见
[partial 类型](partial-types.md)「跨碎片重载 → 静默覆盖」）。若外层已有 `Log(string)` 而转发
生成了 `Log(int)`，用户那份会被**吃掉**，调用点报出一条看不懂的假类型错。

所以 S5 **按名字跳过，arity 不同也跳**——转发不得生成任何与外层同名的方法，哪怕签名不冲突。

## 适用边界：①② 只对**本包**类型

|  | 本包类型 | 跨包类型 |
|---|---|---|
| ③ `partial` 声明档 | ✅ | ✅ |
| ① / ② | ✅ 签名**完全保真** | ❌ 报错（`E0465`） |

**不是保守，是跨包元数据里就没有那些信息**：

- **参数名**在导入时就被丢掉 ⇒ 只能造 `p0/p1` ⇒ 命名实参失效；
- 🔴 **`ref` / `out` 在格式里根本不记录** ⇒ 连「这个方法带不带 `ref`」都判定不了。

而丢掉 `ref` 的后果是**静默的**——调用点少写 `ref` 照样编译通过、修改直接丢失。
「判定不了 + 错了不响」只能整类拒绝。跨包转发请用 ③ 档：签名由你手写，`ref` 你自己写对。

## 诊断

| 码 | 场景 |
|---|---|
| `E0464` | 点名的成员**不在这个字段的类型上**；`typeof(...)` 不是接口；实参形状不对 |
| `E0465` | ①② 用在跨包类型上（渲染不出等价签名）；或目标是私有成员 |
| `E0466` | 无法唯一确定目标：名字有多个重载，或目标是 Object 协议方法 |
| `I0467` | 【Info】外层已声明同名 → 跳过。**不是错误**，但必须说出来 |

诊断是**分层**的：`methodof` 先报「`X.M` 不存在 / 有歧义」，`[Forward]` 再报「它不在这个字段
的类型上 / 转发不了」。两层各管各的判断。

## 生成的源码在哪

generator 生成的是**源码**（而不是直接造 AST/IR），并且**会落盘**——栈帧里出现 `__gen$…z42`
时，背后有一个真文件可以打开：

```toml
[build]
generated_dir = "…"      # 没配置 → <output_dir>/generated；配 "" → 不落盘
```

**配的是「写到哪」而不是「写不写」**：只要有 generator 产出就写，不需要「先想起来开个开关、
再重编一次」。没用 generator 的包一个字节都不写。显式 `generated_dir = ""` 表示关闭
（只读文件系统 / CI 不想要额外产物）。

🔴 **这个目录必须在 `[sources] include` 扫描范围之外**，否则下次构建会把生成的 partial 碎片
当成**用户源码再编一遍**，直接踩上面 S5 那个静默覆盖——**你自己的方法会消失**。配错会被
**报错拒绝**（默认值在 `artifacts/` 之下，天然安全）。

> 落盘产物**不参与编译输入**：连编两次产物字节相同。

## 不在本特性范围内

- **转发字段 / 属性**：v1 只转发方法。
- **递归 / 传递转发**（S3 明确不做）。
- **IDE 的 Find All References / rename**：依赖 roadmap 0.5.7 的 `z42-lsp` 里程碑。

## 为什么是生成真方法，而不是名字解析改写

曾考虑在绑定期把 `a.c` 改写成 `a.b.c`。否决原因：要立一条「名字级」新公理、碰重载决议器、
加绑定期可见性豁免钩子（无先例），**而且做不到接口满足与反射可见**。

Lombok `@Delegate` / Kotlin `by` / Rust RFC 2393 **全是生成真方法**，没有一门语言用纯名字解析。
