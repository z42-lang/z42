# Design: 引用类型的空检查标记

## Architecture

```
签名文本（跨包已能携带）        编译期事实通道（新）            诊断
──────────────────────         ──────────────────            ──────
IPAddress? TryParse(...)   →   返回值标记位 = Marked      →   调用点：结果为 MaybeNull
void F(string? s)          →   形参标记位 = Marked        →   被调方：s 为 MaybeNull
string? Name;              →   字段标记位 = Marked        →   读出即 MaybeNull
（未标）                    →   Unmarked = 不强制          →   视为 NotNull，无诊断

                    ┌─ 义务点（解引用 / return 传播）→ 未窄化则报错
MaybeNull 事实 ─────┼─ 窄化（== null 早退 / != null / is / && / ?: / 赋非空）→ NotNull
                    └─ Expect("理由") → NotNull（运行期真检查）
```

**`?` 不进入 `Z42Type`。** 类型相等、可赋性、重载决议、泛型代换、ABI 全部不受影响。

---

## Decisions

### D1：标记位的载体 —— 签名，不是类型

| 载体 | 位置 |
|---|---|
| `MethodSymbol` | 每形参一位 + 返回值一位 |
| `FieldSymbol` | 一位 |
| 跨包 | **签名文本已经在携带**：`TypeNameResolver.TsigTypeName` 给 `NullableType` 拼 `"?"`，`StubEmitter` 拼回。符号加载侧解析回标记位即可 |
| `Z42Type` | **不动** |

`SymbolTable.z42:590` 的 `NullableType` 分支：值类型 → 报错（前一个 change）；
引用类型 → 仍返回 inner 类型（类型身份不变），但**沿途记下标记位**。

**这条是整个设计的地基**：`List<string>` 与 `List<string?>` 因此是同一个类型 ⇒
没有变型问题、没有无约束 `T?` 的含义地狱、`default(T)` 不用解释。

### D2：缺席 = 不强制（而非"保证非空"）

C# 的传染源是「缺席 = 保证非空」：改一个签名，调用方被迫继续往上标。
本设计把缺席定义为「**没说**」：

| 改动 | 结果 |
|---|---|
| 给签名**加** `?` | 只在**直接**调用点产生新诊断，不顺链炸开 |
| 给签名**去** `?` | 永远不破坏任何人 |
| 完全不标 | 今天的行为，一字不变 |

**代价：不健全，会漏。** 未标而实际返回 null 的函数不产生义务。
反向推导（D8）能抓住其中"亲眼看见 `return null;`"的那部分，抓不到间接的。

⇒ **命名必须是「空检查」而非「空安全」。** 写进 reference 文档。

### D3：流分析的结构

语义层现无任何流分析。需要新建：

| 组件 | 说明 |
|---|---|
| 事实格 | `NotNull` / `MaybeNull` / `Null` / `Unknown`（未约束泛型 `T` 取 Unknown，不报不窄化） |
| 事实表 | 键 = 存储路径（局部变量 / 形参）。**字段不入表**（见 D4） |
| 结构化数据流 | **没有 `goto`** ⇒ 不建 CFG，按 `BoundStmt` 递归 + join |
| 正常结束分析 | 早 `return`/`throw`/`break`/`continue` 的窄化要用它；现在也没有 |
| join 规则 | if 两分支 / while（入口取循环前与循环尾的 meet）/ switch / try-catch |

**try/catch 的坑**：try 块里赋的值在 catch 里**不算**已窄化 —— 异常可能在赋值语句之前抛出。
catch 入口的事实 = try 区间内所有程序点的 meet。

**建议先做 `add-definite-assignment` 复用同一套设施**：DA 的误报率天然接近零
（「用了没赋值的变量」是确定性事实），引擎的 bug 会立刻暴露，而不是混在一堆可疑误报里。

### D4：字段不窄化 —— 必须先快照

```z42
var n = this.Name;  if (n != null) { n.M(); }      // ✅
if (this.Name != null) { this.Name.M(); }          // ❌ 照样报
```

**三条理由，缺一不可：**

1. **属性会被读两次**。若 `Name` 是带 getter 的属性，`if (this.Name != null) { this.Name.M(); }`
   是**两次调用**，返回值可以不同。允许窄化在这里直接是错的
2. **多线程**。别的线程能在检查与使用之间把字段置空。只有快照到局部（单次读）安全
3. **可预测**。永不出现「我明明检查过了，为什么这里报那里不报」

C# 选的是"调用即失效"，代价是不可预测——用户检查完顺手写句日志就要重新检查。

摩擦面由 User 自己控制：只作用于**标记过的**字段。

> **✅ Q1 已实测（2026-09-22）：取 (a)。** 两条都实现、各跑一次全仓：
> (a) 51 处命中、形态单一；(b) 7 处，但**那 7 处全是「检查完插了一次无关调用」**——
> `LinkedList` 里相邻两行同一个表达式一行报一行不报、`HttpClient` 里取个时间戳就要重查、
> `Decl.MergeParseDiags` 里 `while` 条件合法而体内报错。少报的 44 处买回来的正是
> 「我明明检查过了，为什么这里报那里不报」。详细数据与站点见 proposal 的 Q1 小节。
>
> 又：**标记是 opt-in ⇒ 存量迁移量为 0**（全仓现有 `?` 字段 = 0），那 51 是上界不是欠账。

### D5：`Expect("理由")`

| | |
|---|---|
| 形态 | 编译器 intrinsic，**唯一**允许作用在 MaybeNull 值上的成员访问 |
| 参数 | **必须给，且必须是字符串字面量**。不提供无参版本 |
| 运行期 | 真检查。为 null 则抛，消息 = 理由 + 源位置 |
| 结果 | NotNull，义务解除 |

**为什么必须带理由**：C# 的 `!` 是纯编译期擦除——不检查、不留痕、不解释。
Rust 的 `expect(msg)` 是真 panic 且带消息。强制理由参数把"为什么你认为它非空"
变成代码里可 grep、可计数、可在 review 里数的东西。

### D6：砍 `??` / `?.` 的迁移

| | 生产 | 测试 | 做法 |
|---|---|---|---|
| `??` | 69（compiler 47 / stdlib 22） | 42 | 机械改写为 if / 局部变量 |
| `?.` | **0**（z42 代码里实际仅 3 处，均在 `tests/control_flow/null_conditional.z42`） | 3 | 删测试 + 删 `ExprTyper.z42:385` 脱糖 + 删 AST 节点 |

`?.` 的其余 grep 命中是注释，或 android/ios appbuilder 里**生成的 Kotlin/Swift 源串**
（`dest.parentFile?.mkdirs()`），与 z42 语法无关，**不动**。

**顺序**：`Expect` 先落地，再砍 `??` —— 否则有一段时间用户既没有 `??` 也没有逃逸口。

**自举**：编译器自身用了 47 处 `??`，改写后必须能编自己。按 `bootstrap-seed.md` 走冷种子。

### D7：override / 接口一致性

| 位置 | 允许 | 禁止 | 理由 |
|---|---|---|---|
| 返回类型 | 子类**去** `?` | 子类**加** `?` | 加了之后，经基类调用的人没有义务 → 洞 |
| 形参 | 子类**加** `?` | 子类**去** `?` | 去了之后，基类契约允许传 null，子类却不检查 → 洞 |

（协变/逆变方向，与类型系统的常规一致。）

### D8：反向推导

函数体里有 `return null;`（字面量）而返回类型未标 `?` → 诊断，提示加 `?`。

- 「亲眼看见」级别，**零误报**
- 让标注几乎自动完成，解决「没人标 ⇒ 机制不生效」的覆盖率问题
- 成本几乎为零（同一套流分析里的一个 Null 事实）
- **抓不到**间接情形（`return other.MaybeNullCall();`）—— 这是 D2 不健全性的一部分，接受

### D9：错误码

| 码 | 条件 |
|---|---|
| `PossibleNullDereference` | 对 MaybeNull 值解引用（义务点） |
| `PossibleNullReturn` | 把 MaybeNull 值 `return` 给未标 `?` 的返回类型 |
| `NullableFieldNotSnapshotted`（**E0484**） | 直接解引用标 `?` 的字段/属性（消息给出快照写法）。与形参的 E0478 分成两码，因为**修法不同**：形参就地 `if (s != null)` 就够，字段必须快照 |
| `UnmarkedNullReturn` | 反向推导：函数体 `return null;` 但返回类型未标 |
| `NullableOverrideMismatch` | override / 接口实现的 `?` 方向违规 |
| `ExpectRequiresLiteralReason` | `Expect()` 无参或参数非字符串字面量 |
| `ObsoleteNullOperator` | 使用 `??` 或 `?.`；消息给迁移写法 |

**级别：error，且总是开启。** 不做 per-package 开关——标记本身就是 opt-in 机制，
再加一层开关只会让"标了但没生效"成为新的困惑来源。

### D10：分阶段开闸（本变更内部）

| | 内容 | 目的 |
|---|---|---|
| A | 引擎 + **只报 `Null`（亲眼看见被赋成 null）** | 零误报地验证引擎 |
| B | `Expect` 落地 | 开闸前必须有逃逸口 |
| C | 标记 → MaybeNull，义务点全开 | 主体 |
| D | 反向推导 | 覆盖率 |
| E | 砍 `??` / `?.` | 迁移 |

A 阶段不接受任何误报 —— 有误报说明引擎有 bug，不是规则太严。

## Risks

| 风险 | 缓解 |
|---|---|
| 引擎误报 | D10 阶段 A：只报确定性事实，零误报为通过标准 |
| 迁移量（`??` 69+42 处） | 机械改写；自举走冷种子 |
| Q1 字段规则选错 | ✅ 已实测消解：两条规则各跑一次全仓，取 (a)（见 §D4） |
| 跨包标记丢失 | 签名文本已携带 `?`；须有跨包用例（参考 `tests/cross-zpkg/`） |
| 被当成"空安全"而过度信任 | 文档命名为「空检查」；reference 页显式写明不健全与漏的形态 |

**不涉及**：运行期表示、ABI、zbc/zpkg 格式 bump、GC、JIT。
`Expect` 的运行期检查复用现有空引用异常路径。
