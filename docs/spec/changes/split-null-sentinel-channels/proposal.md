# 给 `Value::Null` 的各义分出专属通道（审计 R3 的根治）

> 类型：**vm**（+ 少量 lang 面）｜ 创建：2026-09-27｜ 状态：**本线收口**（2026-09-28）—— 逐条测量后：②① 正当不动 · ③ 无可达缺陷 · ④ 完成 · ⑤ 修三处 · ⑥ 完成
> 出身：结构审计 2026-09 的 **R3**。审计原话：`Value::Null` 是**六义哨兵**，
> #822/#837/#838/继承字段 Null/`PrimModel` 静态表读成 Null「不是五个 bug，是一个表示缺陷的五张脸」。
> 前序：**#906**（基元字段写 Null 静默无效）+ **#908**（数组元素同形）—— 已堵写侧两格。

## 0. 收口结论（2026-09-28）：审计的「六义都要拆」是**过度概括**

这条线做完之后，最有价值的产物不是代码，是这张表 —— 它只能靠**逐条测量**得到，
照搬审计的提法会做掉一半不该做的工作。

| # | 含义 | 结论 | 依据 |
|---|---|---|---|
| ① | 用户的 `null` | ✅ **正当，一个字未动** | 这就是 `Null` 该表示的东西 |
| ② | 引用类型的零值 | ✅ **正当，一个字未动** | 对引用类型 `null` **就是**零值。不是混用，是定义 |
| ③ | **缺席** | ⚠️ **无可达缺陷 ⇒ 不做** | `field_value` 确实把**五种**含义压成 Null（槽越界 / ref 槽越界 / `TAG_UNKNOWN` struct 根 / `decode_prim` 失败 / 真的是 null）—— 但反射入口**先按名字在目标自身类型上定槽**（找不到即 bail）⇒ 越界那几格**不可达**。**不凭判断改** |
| ④ | **void** | ✅ **builtin 那半完成（#912）；函数那半判定*不该*做** | builtin 有真实误用被 `exec_builtin_value` 当场抓到（`__println` 的结果被当值用）。函数那半：`voidMethod.Invoke` 返 `null` **正是 C# 的契约**、内部 dst 寄存器无可观测后果 ⇒ 改它要动 `Frame::ret`、跨 11 处，而边界上**仍得返回 null** —— 纯支出 |
| ⑤ | **失败被吞** | ✅ **修三处** | #906 基元字段 ← Null 静默无效 · #908 数组元素 ← 类型不符静默清零 · #917 struct 字段 ← 非同型**半写坏** |
| ⑥ | **缺参** | ✅ **完成（#918）** | 11 个 builtin 补局部 arity 校验；`args.get(N).unwrap_or(Value::Null)` 形态全仓清零 |

⇒ **实打实要修的只有 ⑤⑥。** ①② 是正确的；③ 没有可达缺陷；④ 一半该做一半不该做。

### 这条线上被测量推翻的三个判断（都是我自己的）

1. **「加 `Value` 变体后编译器会逐个告诉我们」** —— 实测只报 **3** 处（E0004），
   而 **251 处 `_ =>`** 会静默吸收新变体；改签名（方案 C）则报 **51** 处。
   **类型强制与约定强制的差别就是 51 比 3。**
2. **「90 处 `Ok(Value::Null)` 都是 void」** —— 权威清单从 stdlib `[Native]` 声明推导只有 **45** 个；
   另一半在**有返回值**的 builtin 里，`Null` 是它们的合法返回。机械替换会改坏一半。
3. **「有变长 builtin ⇒ arity 不是单个数字，所以要独立设计一道门」** ——
   **没有真正变长的 builtin**（切片技巧 / 松散找参 / 校验的是别人的 arity）。
   门确实不该做，但真正的理由是「307 个里只有 80 个函数体字面索引 `args`」⇒ 无从提取、必假红。

### 一条可复用的判据

⭐⭐⭐ **「一个值承载 N 种含义」不等于「N 种都该拆」。** 先逐条问两件事：
**(a) 这个含义用 `Null` 表示是不是本来就对？**（①② 是）
**(b) 混用能不能被用户走到？**（③ 走不到、④ 的函数那半外部契约本就是 null）
只有两问都过不去的才该动 —— 否则会把正确的行为改坏，或付出零收益的改动面。

## 1. 先更正审计的提法：六义里**两个是正当的**

「六义哨兵」听起来六个都该拆。逐条看下来不是：

| # | 含义 | 判定 | 理由 |
|---|---|---|---|
| ① | **用户的 `null`**（`null` 字面量、引用变量置空） | ✅ **正当，保留** | 这就是 `Null` 该表示的东西 |
| ② | **引用类型的零值 / 未初始化** | ✅ **正当，保留** | 对引用类型，`null` **就是**它的零值。这不是混用，是定义 |
| ③ | **缺席**（查不到 / 读不到 / 无此项） | 🔴 混用 | 「没有这一项」与「这一项的值是 null」被压成同一个值 |
| ④ | **void**（builtin 没有返回值） | 🔴 混用 | 「不返回任何东西」被表示成「返回 null」 |
| ⑤ | **失败被吞**（`decode(..).unwrap_or(Null)`） | 🔴 混用 | 一次**错误**被表示成一个**值** |
| ⑥ | **缺参**（`args.get(N).unwrap_or(Null)`） | 🔴 混用 | 「少传了参数」与「显式传 null」无法区分 |

⇒ **根治的对象是 ③④⑤⑥，不是六个。** ①② 一个字不该动 —— 改它们才会制造新 bug。

> ⭐ **#906 / #908 已经各修掉一处 ⑤**（`let _ = encode_prim(..)` ⇒ 传播错误）。
> 本刀是同一条线的继续，不是重新开始。

## 2. 测量（`src/runtime/src`，排除测试）

| 用法 | 处数 | 主要承载 |
|---|---|---|
| `Ok(Value::Null)` | **90** | ④ void |
| `unwrap_or(Value::Null)` | **55** | ③ / ⑤ / ⑥ 混在一起 |
| 其中 `args.get(N)/first().cloned().unwrap_or(Value::Null)` | **22** | ⑥ 缺参 |
| `matches!(.., Value::Null)` | 24 | 消费侧判空 |
| `Value::Null =>` | 13 | match 分支 |
| `= Value::Null` / `vec![Value::Null` | 8 / 6 | ② 置空 / 零初始化（**正当**） |

**④ 一家占 90 处**，是最大的单一含义，也是最机械可改的一类。

### 顺带量出一个缺口：builtin 的 arity **没有门**

`corelib/native_decl_tests.rs` 双向对账 stdlib 的 `[Native("__x")]` 与 VM 的 `BUILTINS`
—— **只对名字，不对参数个数**。而那 22 处 `args.get(N).unwrap_or(Value::Null)` 意味着：
**stdlib 声明与 Rust builtin 的 arity 一旦错配，缺的参数被静默替成 `Null`**，
表现为 builtin 深处一个莫名的 Null，而不是「arity 不符」。

那道门自己的抬头写着它存在的理由是「在此之前漂移的第一个征兆是运行期 `unknown builtin` panic，
**而且只在那条路真跑到时才出现**」。arity 是同一个道理的下一格。

## 🔴 实测推翻了我给方案 A 的安全性论证

我在 §3 把「每个穷尽 match 都要加臂 —— **但编译器会逐个告诉我们**（这是好事）」写成方案 A 的
优点。**那句话是错的**，实验证据：

在 `Value` 上临时加 `Void = 19` / `Absent = 20` 两个 unit 变体、`cargo check --lib`：

| 量 | 数 |
|---|---|
| 非穷尽 match 报错（E0004） | **3 处**（`value.rs:273` / `convert.rs:264` / `alloc.rs:530`） |
| 提到 `Value::` 的文件里的 `_ =>` 兜底臂 | **251 处** |

⇒ 绝大多数 match 都有 `_ =>`，**加变体编译器几乎什么都不报**；新变体会**静默落进兜底臂**
被当成「某个别的值」。A 的改动面看着小（3 个错误）恰恰因为它的**风险面大**（251 处静默吸收点，
且没有任何机制能把它们找出来）。

**对比 C（已落地）**：改签名后编译器报了 **51 处**，逐个指到该改的地方 ——
**类型强制 vs 约定强制的差别，就是 51 比 3。**

⇒ User 据此改选 **C**。我先前把 C 判为「改动面比 A 更大」也是错的：它的**改动面**确实更大，
但我当时只比了改动面、没比风险面。

## 4′. 裁决结果与 ④ 的落地（2026-09-27）

| 裁决点 | 结论 |
|---|---|
| 方案 | **C —— 不动 `Value`，全靠类型强制** |
| `Void` 泄漏到用户面 | **无条件报错**（两个 profile） |
| arity 门 | **加，且先于 ⑥ 落地** |

### ④ void：已实施

```rust
pub type NativeFn     = fn(&VmContext, &[Value]) -> Result<Value>;
pub type NativeVoidFn = fn(&VmContext, &[Value]) -> Result<()>;   // 类型上无法产出值
pub enum Native { Val(NativeFn), Void(NativeVoidFn) }             // 表项，下标一个不变
```

- 分发 `exec_builtin{,_by_id}` 返回 **`Result<Option<Value>>`**（`None` = void）
  ⇒ `Option` **强制**调用方处理 void 那一格。
- **interp**（`exec_call.rs`）与 **jit**（`jit/helpers/call.rs`）双侧：`Ok(None)` 时**不写 `dst`**。
  此前 void builtin 返回 `Ok(Value::Null)`、两侧都无条件 `set(dst, Null)` ⇒ 「无返回值」与
  「返回 null」在寄存器里长得一模一样。
- 给「明确期待有返回值」的调用方加 `exec_builtin_value`（撞上 void 报错），
  这就是裁决②「无条件报错」的落点 —— **不是**在寄存器里见到就报（那会让每次 void 调用立刻炸），
  而是在**值被当值用**的那一刻报。

### 🔴 权威清单是 **45**，不是 90

`Ok(Value::Null)` 全仓 **90** 处，但 void builtin 的**权威清单从 stdlib 的 `[Native]` 声明推导**
（返回类型是否 `void`）= **45** 个。另外那 ~45 处在**有返回值**的 builtin 里，
`Null` 是它们的**合法返回**（含义 ①，如 `Type.GetType` 查不到返 null）。

⇒ **机械替换全部 90 处会改坏一半。** 这是「从声明推导」而不是「grep 计数」换来的。

### 新边界当场抓到的旧债

- 一处把 **void builtin 的结果当值用**的调用点（`__println` 经 `exec_builtin_value`）；
- 几条测试在**断言那个哨兵本身** —— 测试名就叫 `drop_unknown_slot_is_silent_null`，
  它为 void builtin 断言 `matches!(r, Value::Null)`。已改为断言「调用成功」并去掉名字里的 `_null`。

### 闭环门：`declared_voidness_matches_the_builtin_table`

`Native::Val`/`Void` 是**手写的第三份数据**，必须与 stdlib 的返回类型一致。
门装进既有的 `native_decl_tests.rs`（它已双向对账名字，这是第三条）。

⚠️ **只改「味」编不过**（签名不匹配），所以类型系统已兜住那个方向。门真正防的是另一个方向：
**新 builtin 在 stdlib 声明成 `void`，却登记为 `Native::Val` + 返回 `Ok(Value::Null)`** ——
那**编得过**，且悄悄退回旧的混用。

**阴性对照**（按这个方向做）：把 `__env_unset` 的声明临时从 `void` 改成 `string`，门精确报

```
__env_unset: stdlib 声明有返回值，而 BUILTINS 登记为 Native::Void  (z42.core/src/IO/Environment.z42:35)
```

⚠️ 这道门的启发式**第一版写错过**（从关闭引号切 tail、没跳过引号 ⇒ 对全部 45 个都误报）。
是门自己把这个错暴露出来的 —— 也说明它对「不一致」确实敏感。

### 顺带修的规范冲突

`builtin_table.rs` 抬头写「BuiltinId **会被烤进 zbc**，中间插入会让既有产物错位」，
而 `builtin_table_ext.rs` 抬头记着（2026-09-26 读码核实）**那句话不成立** ——
zbc 存的是**名字**，`BuiltinId` 是加载期填的单次运行令牌。两份互相矛盾，
已以核实过的那份为准更正（`CLAUDE.md` 的规范冲突检测）。

### 仍未做（③⑤⑥）

| 含义 | 状态 |
|---|---|
| ⑤ 失败 | #906 / #908 各修一处；其余 `unwrap_or(Value::Null)` 未逐处审 |
| ③ 缺席 | 未做（`Option<Value>`，需逐处判断「这里是缺席还是真 null」）|
| ⑥ 缺参 | **被 arity 门阻塞**（裁决③：门先于 ⑥）；而 arity 门本身**需要自己一轮设计** —— 见下 |

### ⚠️ arity 门：本刀不做，理由是实测

原以为「给 `native_decl_tests` 加 arity 对账」与 void 那条同款廉价。实测不是：

- **Rust 侧从不声明 arity**（`NativeFn` 收 `&[Value]`）⇒ 无处可对账；
- 表有 **307** 项，手写 arity 不现实且与实现容易漂；
- **确实有变长 builtin**（`&args[1..]`、`args.iter()`、6 处按 `args.len()` 分支）
  ⇒ arity 不是单个数字；
- 从 Rust 源里扫 `args.get(N)` 的最大下标属启发式，且要处理 `this` 偏移
  —— **假红风险高，而本仓有明确教训：假红比没门更坏**。

⇒ 它需要独立一轮设计（大概要让表带 `(min_arity, variadic)` 并由门从 stdlib 声明反向核对）。
**不在本刀仓促上一个可能假红的门。**

## 3. 三个方案

### 方案 A：加两个 unit 变体 —— `Value::Void` + `Value::Absent`

```rust
Null    = 5,   // ①② 用户的 null / 引用零值（语义收窄为「就是 null」）
Void    = ?,   // ④ 无返回值
Absent  = ?,   // ③ 查不到 / 无此项
```

- ⑤ 失败 → **不给变体**，走 `Result`（#906/#908 的做法，已验证）
- ⑥ 缺参 → **不给变体**，走 arity 错误 + 补门

| 优点 | 缺点 |
|---|---|
| `Value` 是 16 B，unit 变体**零尺寸代价**（判别值已是 u8，还有空位） | 每个对 `Value` 穷尽 match 的地方都要加臂 —— 但**编译器会逐个告诉我们**（这是好事，不是负担）|
| 消费侧从此能分辨「没有」与「是 null」 | 90 + 若干处要改；跨 interp/jit/corelib/反射 |
| ⑤⑥ 复用已验证的错误通道，不扩表示 | `Void` 若泄漏到用户可见处（打印 / 装箱）要有明确规则 |

### 方案 B：只分 `Void`（最小刀）

只做 ④ 那 90 处；③ 留 `Null`。收益窄，但**机械、可逐处核对、回归面小**。

### 方案 C：不加变体，改 Rust 侧签名

③ → `Option<Value>`；④ → builtin 表分出「无返回值」那一类的签名。更 Rust 地道、
`Value` 一个字不动；但 builtin 共用 `fn(&VmContext, &[Value]) -> Result<Value>`，
拆签名要动分发表与全部 90 个 builtin 的注册形态 —— **改动面比 A 更大**，且
寄存器里流动的仍是 `Value`，④ 在 VM 内部依然需要某个值来占位。

## 4. 需要 User 定的三点

1. **范围**：A（Void + Absent 一起）/ B（只 Void）/ C（改签名）？
   ⚠️ 我倾向 **A，但分阶段落地**：P1 只做 `Void`（90 处，机械），P2 再做 `Absent`（③ 逐处判断）。
   理由：`Void` 是最大的一类且改法无歧义；`Absent` 需要逐个判断「这里到底是缺席还是真 null」，
   混在一起做会让 review 无法分辨两类改动。
2. **`Void` 泄漏到用户面时的规则**：z42 代码本不该拿到它（void 调用无结果寄存器）。
   若因某条路拿到了 —— **debug `bail!` / release 当 `Null`**（#837 先例），还是**无条件报错**？
   我倾向前者：那是 VM 内部不变式被破坏，不是用户的错。
3. **arity 门**：顺带给 `native_decl_tests.rs` 加 arity 对账吗？
   ⚠️ 它是 ⑥ 能安全改成硬错误的**前置**（不然一次错配会从「静默 Null」变成「运行期崩」）。
   我建议**加**，且**先于** ⑥ 落地。

## 5. 验收判据

- **每阶段独立 GREEN**，且每阶段都要有**阴性对照**（撤回该阶段 ⇒ 对应用例精确变红）。
- **①② 不得变**：引用字段/数组元素写 `null` 仍合法、`default(T)` 对引用类型仍是 `null`
  —— 这三条是回归门，缺一不可（#906/#908 的教训：不钉住「本该合法」的那侧，
  「把整条路堵死」也会让正例变绿）。
- `cargo test --lib`（不带过滤）+ `xtask test e2e` + `test stdlib` + `test compiler` + `test docs`。
- 预期**零格式 bump**（`Value` 是运行期表示，不进 wire）；**指纹按「诊断/发码是否变」逐阶段判**。

## 6. 不做

- **不动 ①②**（见 §1）。
- **不把 ⑤ 变成变体** —— 错误就该走 `Result`，#906/#908 已验证这条路。
- **不在本刀做 `Value` 的尺寸/表示优化**（那是 `z42-memory-footprint-analysis` 那条线）。
