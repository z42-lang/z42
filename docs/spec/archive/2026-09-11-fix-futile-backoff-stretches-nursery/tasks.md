# Tasks: fix-futile-backoff-stretches-nursery

> 状态：🟢 已完成 | 创建：2026-09-11 | 完成：2026-09-11

**变更说明：** 收窄自动回收「徒劳退避」的判据 —— 去掉「回收量不到**半个**闸门 ⇒ 倍数翻倍」
这一档，只保留 `FUTILE_DIVISOR`（闸门的 1/16）那一档。

**原因：** 倍数乘的是 **nursery**，而 nursery 不是内存闸门，它是「一次 minor 要啃多大一片
年轻代」的上界，也就是停顿上界。判据一宽，「这个程序存活率高」得到的回应就成了「那下次多扫
四倍」，方向正好反。半个闸门这条线分不开两种都「回收得少」的形状：

| 形状 | 实测（同为 32 MB 闸门） | 该怎么办 |
|---|---|---|
| **真徒劳**：活集合根本不产生垃圾 | `09_alloc_ctorless`：384 B、然后 0 B | 退避（且不花钱，见下） |
| **只是存活率高**：程序正把大部分分配物留在手里 | `z42c.semantics`：8.4 MB、10.1 MB（闸门的 26% / 32%） | **不该退避** |

后者被判成徒劳、倍数推到 4，于是紧随其后的两次 minor 扫了 96 MB / 160 MB 的年轻代、停了
**45.4 / 64.6 ms**，占整次构建停顿的 39%；同一跑里闸门正常的 minor 只要 6–22 ms。

**文档影响：** book 新增「「回收得少」不等于「徒劳」」一节；`DEFAULT_NURSERY_BYTES` 的档位表
用诚实闸门重测并替换；页头「对齐」块顺带修好（经 User 授权）。

## ☠️ 走过的弯路（第一版方案 A，已否决）

方案 A 是「**没有软上限就不退避**」，理由取自模块文档自己的说法：「余量是 `live × 0.33`，
随活集合一起长，回收次数对堆增长已经是对数的，退避如今只是软上限把余量压到下界那一档的兜底」。

**这个理由只对 major 成立。** minor 的闸门是 nursery，**绝对值**，不随活集合长——所以「相对
余量已经钝化了失控」这半句根本覆盖不到 minor。方案 A 在 `z42c.semantics` 上和 B 一样好，
但在 `09_alloc_ctorless` 上**墙钟 +78%**：那里退避是对的，而 A 把它整个关掉了。

教训：**判据错了、结论对了**，是最难发现的一种错。第一版只量了一个负载就以为成立；抓住它的
是「拿第二个负载验证全局默认值」这一步，而不是任何测试。
