# Proposal: 应用自定义配置属性（add-app-properties）

> 状态：🔴 DRAFT | 创建：2026-09-05 | 类型：`vm` + `lang/工程模型` → 完整流程
> 前置：`complete-runtime-settings`（#443）/ `sidecar-reaches-published-apps`（#446）/
> `app-config-follows-the-app`（#458）—— 侧车机制已通到所有运行形态
> User 裁决（2026-09-05）：① 用户属性是**项目配置**，**不走五层链**，运行时读得到即可；
> ② **支持完整类型**，避免以后再扩展

---

## Why

侧车机制现在能把工程 `[profile.*]` 的**运行时旋钮**送到每一种运行形态。但 app 想携带
**自己的**配置项——API 端点、feature flag、限额——这条管子只修了一半。实测：

```toml
[profile.debug]
mode = "interp"
my-api-endpoint = "https://example.com"
feature-x-enabled = true
```

| | 现状 |
|---|---|
| 流到侧车 | ✅ 生成器不挑，两个键都写进了 `dist/app.runtimeconfig.toml` 的 `[runtime]` |
| 运行时读得到 | ❌ `RuntimeConfig.Get("my-api-endpoint")` → `null` |
| 诊断 | ❌ 每次跑该 app 都刷 `unknown runtime knob ... ignored` ×2 |

**写的一半通了，读的一半没有，而诊断还在反着拦。** 这正是 .NET 的
`runtimeOptions.configProperties` + `AppContext.GetData` 覆盖的场景，z42 目前缺。

---

## What

### A. manifest：`[properties]` 与旋钮**分表**

```toml
[properties]                       # 基表：所有 profile 共用
app-name = "demo"
limits = { max-retries = 3 }

[profile.debug]
mode = "interp"                    # VM 旋钮：登记表校验、类型 / 可用性 / 诊断

[profile.debug.properties]         # 该 profile 的属性，逐 key 覆盖基表
api-endpoint = "http://localhost:8080"
feature-flags = ["x", "y"]
```

**为什么分表而不是靠前缀约定**：VM 旋钮与用户属性必须**结构上**可区分，否则
`gc-mdoe` 这种 typo 会被当成"用户自定义属性"静默收下，那道「未知旋钮就报出来」的诊断
就死了。dotnet 用前缀（`System.GC.*` 归 runtime、其余归 app），但 z42 的旋钮 key 没有
统一前缀（`gc-mode` / `libs` / `log`），走前缀路线等于给所有现有 key 改名。

### B. 侧车：`[properties]` 段，**完整 TOML 类型**

```toml
# generated by z42c build — do not edit
[runtime]
mode = "interp"

[properties]
app-name = "demo"
api-endpoint = "http://localhost:8080"
feature-flags = ["x", "y"]
[properties.limits]
max-retries = 3
```

数组、嵌套表、日期——TOML 有什么就支持什么。`z42.toml` 已有 `TomlValue.Stringify`
（完整往返序列化），生成器直接用，不自己拼字符串。

### C. 运行时：只读、不走链、不校验

- **来源只有 app 侧车**（`Z42_APP_CONFIG` 或由 app 文件推导）。不参与 CLI / env /
  用户配置的分层——按 User 裁决①，它是**项目**配置，不是运行时旋钮。
- **不校验、不诊断**：它不在 `KNOWN_KNOBS` 里，VM 不理解它的含义，也不该假装理解。
- 用户配置（`Z42_CONFIG`）里写 `[properties]` → 一行 warn 说明它归 app 所有、被忽略
  （静默吞掉会让人 debug 半天）。

### D. 脚本表面：`Std.Runtime.AppProperties`

```z42
using Std.Runtime;

string? ep = AppProperties.Get("api-endpoint");   // 标量：一次调用，零依赖
bool has   = AppProperties.Has("feature-flags");
string[] n = AppProperties.Names();               // 顶层键

// 结构化（数组 / 嵌套表）：拿原文交给 Std.Toml
using Std.Toml;
TomlValue p = TomlValue.Parse(AppProperties.Raw() ?? "");
long retries = p.Get("limits").Get("max-retries").AsLong();
```

**为什么不是让 VM 暴露一套结构化 ABI**：z42 stdlib 已经有完整的 TOML 解析器，VM 把
`[properties]` 原文交出去即可——简单情形一次 `Get` 搞定、零依赖；结构化情形用现成的
`Std.Toml`，**完整类型开箱即得，将来不需要再扩展**（User 裁决②）。发明一套路径
mini-language 或结构化 marshal，成本高且表达力仍不如直接给 TOML。

**为什么独立于 `RuntimeConfig`**：两者的保证完全不同——旋钮有登记表、类型、可用性判定、
诊断；属性就是个袋子。混进一个 API，"返回 null"会同时意味着"没设"和"这个旋钮不存在"。

---

## What This Does NOT Do

- **不给属性任何分层**（User 裁决①）：没有 `--set` 覆盖、没有 env 覆盖、用户配置文件
  里的 `[properties]` 被忽略。
- **不校验属性的键或值**：VM 不理解它们。
- **不做属性的写入面**：与旋钮一致，运行时只读。
- 不动 `[profile.*]` 里旋钮与构建期键混住的问题（User 已明确暂不处理）。

## 三阶段

| 阶段 | 内容 | 风险 |
|---|---|---|
| **P0** | manifest 模型 + 解析（`[properties]` 基表 + `[profile.<n>.properties]`）| 低 |
| **P1** | 侧车生成用 `TomlValue.Stringify` 写 `[properties]`（顺带把现有手拼 TOML 换掉）| 中（碰自举）|
| **P2** | VM 读取 + 4 个 builtin + `Std.Runtime.AppProperties` + e2e | 中 |
